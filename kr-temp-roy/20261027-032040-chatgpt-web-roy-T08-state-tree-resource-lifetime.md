## 結論一：命令 151 會清空狀態樹，不會在該迴圈同步清空 +0x164 資源槽位

0x004D2F1F 取得 object+0x3F4 的哨兵節點；0x004D2F25 讀取節點；0x004D2F36–0x004D2F4C 逐項經 0x0073EBA0 和 0x0089120C 清理狀態樹節點。
0x004D2F62–0x004D2F79 重設哨兵節點三個連結；0x004D2F7E、0x004D2F84、0x004D2F8A、0x004D2F90 分別將 owner+0x3F8/+0x400/+0x404/+0x408 清零。
這段流程沒有將 +0x164 開始的資源指標逐項歸零。

## 結論二：0x004C9840 以 stateId 索引資源槽位並按需建立

在既有指標非零時，跳過新資源建立而繼續更新狀態樹；因此狀態樹每批重建與資源槽位按需建立是不同生命週期機制。舊狀態消失並不意味資源在同個函式中同步析構；不能排除其他地方後續清理。

## 結論三：所核對的直接索引前沒有明確的 <128 比較

stateId 經 MOVZX 成為非負索引並進入 [esi+ebx*4+0x164]；從函式入口至這個首次索引，沒有可辨識的 stateId < 128 檢查。其他已確認的資源清理會遍歷 128 槽，但此時尚不能確定合法 ID 領域及上游完整驗證。不得僅憑此推論為安全漏洞。
