## A. 主要結論／證據分級

**本次新增直接 BIN confirmed：** 0x45、0x46、0x47、0x6F 確實是四個不同的 S2C application handler；0x46 state0 與 0x64 state0 都可移除 20-slot 排除鍵，但 0x46 還會在 QuestRecord 可取得且 `record+0x08 != 3` 時**追加前置鍵**，以及發出 F438C→mode3 TalkBox；0x6F 用 bitmask 完整**替換**前置列表，而非逐筆 append；0x45 的 `record+0x44` 動作 discriminator 產生其他 Controller／通知效果。此前 0x74 只是單筆追加前置鍵的其中一條原生路徑，不能宣稱唯一 writer。

**跨原稿已直接重新定位**：0x40 state0 的 F438B→mode2、exclusion 加入與候選重建；0x40 state1 的文字通知；0x64/65 exclusion 移除／清表；0x72 vector 清空；0x74 append 及 rebuild。`0x40(state0)` 不是 `0x46(state0)` 的同義操作；前者新增 exclusion，後者在特定條件移除 exclusion，且可加入 prerequisite。

**條件式特定任務套用**：Q15 type2、town5、giver10338、Demand16（來自 T16-124/125 的有限 XML 擷取）；`0x74(key16)` 或 `0x6F` bit16 可令 Demand16 前置通過，仍需 world town5、level、20-slot 與當前候選重建。`0x46(id15,substate0)` 可在 Q15 record 存在及 record+8 !=3 時把 key15 寫進前置鍵，並觸發 mode3 UI；但**不能因此等同官方 Server 已完成 Q15、已發獎、可前往村莊**。

**重要證據邊界**：Table.stp 是 STPD 容器，本段未直接解出完整 QuestInfo.xml；Q15 subtype 精確 XML 值及 type2/type4 的 2800/468 reward 實數，依歷史擷取／待核資料分級。未能取得原版 Server runtime traffic，不能強制推定 0x3F(15) 與 0x40／0x45／0x46 的真實 request/reply 配對。

## B. Native S→C handler table，分辨 Client application payload 與 wire frame

`0x5020B0` 初始化 `0xFAB2A4` 開始每 8 bytes 一槽的 handler table，使用 `(slotVA-0xFAB2A4)/8` 還原索引，與 BIN 寫入立即數相交叉：

| Application index | Handler | 重要 native 路徑 | 功能與辨識要點 |
|---|---|---|---|
| 0x40 | `0x502270` | `F4281`，`F438B→0x5B6D20`；0x500110；0x500240 | `WORD[pkt+2]=questID`, `DWORD[pkt+4]=state`；state0 exclusion 加入+mode2事件、state1文字通知 |
| 0x45 | `0x5027D0` | `0x503D20`, `record+0x44`, `0x422F40→0x561760`, `F4306`, `0x5016F0` | 任務記錄動作 discriminator 分支，type2分支進 Controller，另有 UI 通知，不是 0x40 state1 |
| **0x46** | **`0x502B40`** | `0x5000D0`, `0x44B4E0`, `0x500240`, **F438C** | `WORD[pkt+2]=qid`, `WORD[pkt+4]=substate`；substate0 移 exclusion、record subtype非3時可 append 前置鍵、重建候選，F438C→mode3 |
| 0x47 | `0x503040` | `0x561760` | 直接傳 `WORD[pkt+2]`,`WORD[pkt+4]` 給控制器，不是上面 0x46 完成副作用 |
| 0x64 | `0x5030C0` | `0x5000D0`, `0x500240`, F4280 | 個別 exclusion 刪除及通知；**不加入 prereq** |
| 0x65 | `0x5035D0` | reset 20 slots，F4280 | 批次 exclusion 清除及重建 |
| **0x6F** | **`0x502170`** | `0x44AB70`，`0x44AA10`，`0x500240` | 將 payload DWORD bitset 解碼為 WORD prerequisite IDs 並**覆寫有效列表** |
| 0x72 | `0x5033B0` | set vector end=begin，`0x500240` | prerequisite 有效列表清空 |
| 0x74 | `0x503400` | `0x44B4E0`，`0x500240` | 單筆 `WORD[pkt+2]` prerequisite append；此 helper 不去重 |

以上 `+2`、`+4` 都是**application payload 的偏移**，與 T02 framing mode A02C、header、WSASend 不能混用。`ret 0x0C` 表示 native handler 堆疊清理 3 個參數，不等於應用訊息固定長度 12B；0x6F 尤其取 `[ebp+0x0C]` 作解碼長度，不能硬填固定 wire 長度。

## C. 0x46：新的「移除排除→完成鍵條件寫入→mode3 UI」原生鏈

### C1. 三個不同 substate 出口

1. `0x502C11` 讀取 `WORD[pkt+4]`。只有為 0 時跳入 `0x502C1E` 的第一路；非0時走 `0x502E6E`，其後對 1、2、3、4、5 各有不同通知／場景效果。`WORD[pkt+2]` 是查 QuestInfo／exclusion 的 quest key，與 substate 不可對調。
2. 在 state0：`0x502CF3` `movsx eax, WORD[pkt+2]`；`0x503D20` 查 QuestInfo map。若不存在 record，在 `0x502D5A` 設 `EDI=0` 仍走 `0x5000D0` 移除 exclusion、`0x500240` 重建及 F438C；只有**append prerequisite**需有效 Record 和 `record+8 != 3`。
3. `0x502DBA cmp dword [edi+8],3`：結構不是 `type` 的同義偏移；QuestInfo XML `subtype` 為獨立 attribute，與 `record+8` 資料有原生 loader/copy 關聯。缺當前 Quest15 全 XML 的 subtype 獨立驗證時，應寫 **conditional**，不能宣稱 `0x46(15,state0)` 無條件加入 key15。
4. `0x502DB1` `0x5000D0` 移除排除鍵；在有效 record 且 subtype 非3，`0x502DD0→0x44B4E0` 把 u16 QuestID 加進 `QuestOwner+0x5EB0` vector，**沒有先去重**；`0x502DD8..0x502DE8` 呼叫 selector `0x40F060()+0x8C` 與 `0x500240` 重算候選。該路徑和單獨 `0x74` 是不同 producer，可能針對不同 Server 步驟或一連串事件，**絕不可自作原版 Server 策略**。
5. `0x502E2F..0x502E51` 建構 `0x105B9`、action `0xF438C`，將 packet QuestID 存 `event+0x14` 並交 `0x58AA50`。這不是前段 `0x40` 的 `0xF438B`。即使記憶體配置失敗，也可觀察到零指標支線；無事件實例不可保證 UI 真正顯示。
6. `substate=1` 的 `0x502EA1` 後續是另一套 locale 文字／通知建構路徑，無條件覆蓋 0x46 state0 的結論是不允許的。state2/3/4/5 會用 `0x5854B0→0x58B270` 送出各自的數字消息代碼，不能全算成「任務完成」。非0不會在同一 CFG 走 `0x5000D0+0x44B4E0+0x500240` 的 state0 主路徑。

### C2. F438C 事件派送表直接解碼與 mode3 TalkBox

`0x5B7F93` 讀 `event+0x10` action，`add 0xFFF0BC9C` 建 0-based index，`0x5B8460[index]` 先映射 small index，再讀 `0x5B8394[4*small]` 跳表。直接由原始 `.text` bytes 算出：

| 原始 action | index | small-index | dispatch VA | handler | mode |
|---|---:|---:|---:|---|---:|
| `0xF438A` | 0x26 | 11 | `0x5B7FED` | `0x5B6BE0` | 1 |
| `0xF438B` | 0x27 | 12 | `0x5B7FFF` | `0x5B6D20` | 2 |
| **`0xF438C`** | **0x28** | **13** | **`0x5B8011`** | **`0x5B6E60`** | **3** |

`0x5B6E60` 在 type getter 回 `0x105B9` 時，以 `event+0x14` 取 QuestID、`0x503D20` 查記錄；命中後 `0x5B6F61 push 3`、`0x5B6F64 call 0x636520` 開啟 mode3 TalkBox，並走 `0x74A010`/`0x596E00` 的後續 UI/事件操作。`0x636520` 將 `+0x80` 設為 QuestID、`+0x90` 設為 mode、`+0x84` 設為 giver/selector 參數；mode3 會另查 `0x500F90` 取 UI record 資源。`mode3` 和 mode2 的 UI 入口雖共用 `0x636520`，**彼此的 callback/內容不可互相借稱**，尤其沒有直接的 `mode2→F4402→0x36` 證據。

### C3. Case matrix (application bytes 只是 Client 條件 fixture)

| Handler 輸入範例 | Client 條件式結果 | 不能據此推論 |
|---|---|---|
| `46 00 0F 00 00 00` | Q15 exclusion remove；若有 record、subtype≠3，append key15；候選重建；F438C(QID15)→mode3 | 非官方抓包；不等於 Server 確認全部獎勵 |
| `46 00 0F 00 01 00` | 0x46 非0狀態路徑，偏通知／資源讀取 | 不能據此直接 append key15 |
| `40 00 0F 00 00 00 00 00` | Q15 exclusion insert、F438B(QID15)→mode2、候選重建、type2 控制器 | 與0x46 state0 效果不同 |
| `74 00 0F 00` | append key15 並重建，不建 F438C mode3 TalkBox | 不必然表明 Quest15 已實際遊玩完成 |
| `64 00 0F 00 00 00 00 00` | Q15 exclusion remove+rebuild/通知，不 append 前置 | 不能等同 0x46 state0 |

## D. 0x6F：位元遮罩完整快照重建，非逐筆 0x74

1. `0x5021A2..0x5021D1` 把 `owner+0x5EB4=end` 設回 `begin=owner+0x5EB0`，清空有效前置列表。沒有逐元素 free、沒有清空別的排除列表；與 `0x72` 的有效列表 reset 有相似結果，之後會填回多筆鍵。
2. 第三個 handler 參數 `DWORD[ebp+0x0C]` 被當作 **application bytes 數量相關參數**：`add eax,-2`，`test al,3`。在 `(len-2)%4==0` 時，`0x5021F1` 以 `pkt+2` 提供 DWORD bitmask 序列給 `0x44AB70`；若不對齊，直接跳過 bitmask 複製，但**已 reset prerequisite**，仍會呼叫 `0x44AA10` 與 rebuild。需由 T02 確認外層 length guard，不能將此解讀為安全或合法的畸形 Server frame。
3. `0x44AB70` 以 `eax=(len-2)` 右移2得 DWORD 個數，把輸入 `[pkt+2]` 的各 DWORD 複製到暫存 vector；若新 buffer 容量不足經 `0x6D6240` 擴充。無條件 copy 外部未驗證長度不代表有界安全性。
4. `0x44AA10` 遍歷每個 DWORD mask 的 32 個 bits；`0x44AA53 mov edx,1; shl edx,cl` 以 bit index 偵測 1；設位時 `0x44AA65 add eax,ebx`，其中 `eax=wordIndex*32`、`ebx=bitIndex`；`0x44AA67 movzx edi,ax` 轉 WORD key，append 到 `owner+0x5EB0` WORD vector。0x44AA28 項目數為 `tempEnd-tempBegin`/4。**由 set bits 自然枚舉，每個 index 每次 snapshot 最多產生一次；它和 0x74 的不去重 append 語義不同。**
5. `0x50223F..0x502246` 讀 `0xFAB1BC`（world selector）與 owner，呼叫 `0x500240` 重建候選；bitset 順序由 DWORD index 低到高、bit 低到高。對 Q15 的 Demand16 而言，bit16 set 的 snapshot 足以在前置 gate 符合一筆 key16，但另需 town5 與其他 gate。

**可驗算範例（僅 handler bytes，不含 framing）**：

```text
6F 00 00 00 01 00     # mask0 = 0x00010000; bit16 -> prereq key16
6F 00 00 80 00 00     # mask0 = 0x00008000; bit15 -> prereq key15, 不含key16
6F 00 00 80 01 00     # mask0 = 0x00018000; bits15+16 -> both keys
6F 00 00 00 00 00     # mask0 = zero; reset to empty prereq list
72 00                 # handler不讀額外 key，直接 reset
74 00 10 00           # append a single WORD key16，不同於全列表 snapshot
```

這些是**根據原生位元運算推導的測試資料**，不是從原版 Server 擷取的封包；`0x6F` 呼叫的 payload length 與 framing mode 必須整合 T02，不能把 6 bytes 宣稱完整 wire frame。

### D1. 快照與單筆更新可能互相影響的順序（不猜官方先後）

- `0x74(key16)` 後再 `0x6F(mask=0)`：後者清空有效前置 vector，key16 不存在，Quest15 Demand16 gate 將失敗。
- `0x6F(bit16)` 後再 `0x74(key16)`：後者會**再追加** WORD16，形成重複；候選 Demand16 仍可通過，但不是新的 Server 完成交易。
- `0x72` 後 `0x6F(bit16)`：先 reset 再 snapshot，結果仍只有 bitset 反映的已設 bit。
- `0x46(15,state0)` 若 append key15 後又 `0x6F(bit16 only)`：後者會取代有效列表，key15 失去；Q15 本地完成標記並無保留保證。

## E. 0x45／0x47：不同 UI／Controller 訊息，不是 0x46 state1 的別名

### E1. 0x45（`0x5027D0`）

- `0x5027FB` 取 pkt；`0x502804` 對 `WORD[pkt+2]` 做 sign-extension，`0x503D20` 查 QuestInfo map；未命中直接 exit。
- record `+0x44`（在 QuestInfo parser 的 `CompleteAction/type` XML 分支與 map record copy 相關）經 `sub eax,2`：若值2→`0x502889` 取 `record+0x48`、QuestID 作為兩參數，`0x422F40→0x561760` controller；若值3→`0x50283F` 發出 `F4306` event `event+0x14=record+0x40`；其餘→繼續產生文字／通知。
- 適用於 Quest15 的條件：若 record 完整、其 CompleteAction type 等於2，會進 Controller 分支；但**沒有直接足以確認 Quest15 XML 的 CompleteAction.type 實際值**，不得因此保證 Q15 一定走控制器。且 0x45 不等於 0x40 state1、也不等於 0x46 state0，沒有本體中的 0x44B4E0 prerequisite writer。
- 後段 `0x5016F0` 建文字／UI 使用 record `+0x4C`，`0x5536E0` 與 `0x4D6B30` 等其他通知路徑；這是本地視覺消費／事件，不證實獎勵 type2/type4 實際貨幣增減。

### E2. 0x47（`0x503040`）

`0x503095`：

```asm
mov eax,[ebp+8]           ; application pointer
movsx ecx,WORD[eax+4]    ; secondary
movsx edx,WORD[eax+2]    ; primary/QuestID conditional
push ecx
push edx
mov ecx,0xFB73C0
call 0x561760
```

這是獨立的控制器兩個 WORD input 路徑，沒有直接 `0x500240` 候選重建、`0x44B4E0` prereq 追加、`0xF438C` 事件。示例 `47 00 0F 00 01 00` 僅表示應用層 input `(15,1)`，至於 controller pending gate 和 Scene/C2S 0x3F 的後續則繼承 T16-127，不能由此 handler 保證發包。

## G. 對相容 Server 的準確邊界／測試與後續研究

### G1. Client 待逆向（需記錄，不把超出本段目標的項目冒稱已證）
