## 0. 本段有界結論：四類不同的任務狀態意義

| 入站 *application* opcode | 依 BIN table 的 handler | 從輸入取值 | 原生 Client 可確認的效果 | 不能據此主張 |
|---|---|---|---|---|
| `0x40` | `0x502270` | `WORD [pkt+2]` = QuestID；`DWORD [pkt+4]` = state | state0：`0xF4281`/`0xF438B` 事件、20-slot exclusion writer `0x500110`、`0x500240` 候選重建、依 QuestRecord.type 額外控制器／事件／顯示；state1：查 QuestRecord 並格式化任務文字通知；其餘 state 跳過主要分支 | 不能將 state0 或 state1 直接等同官方「成功接取／完成／拒絕」語義；沒有證明 `0x36` 或 `0x3F` 必然配對 |
| `0x64` | `0x5030C0` | `WORD [pkt+2]` + `DWORD [pkt+4]` | state0：`0xF4280` 事件，`0x5000D0` 移除一個 20-slot exclusion key、呼叫 `0x53DC90`、重建候選，並建立文字／UI 通知物件 | 非 `0x74`，不寫入 prerequisite `+0x5EB0`；不能稱作自動完成 Q16 |
| `0x65` | `0x5035D0` | `DWORD [pkt+2]` 在 state0 gate；另產生 `0xF4280` 事件 | state0：逐 20-slot exclusion key 呼叫 `0x53DC90`、清零每個 WORD，重新候選計算，另建立 UI 通知 | 它不是 `0x64` 的單一 QuestID 刪除，不能憑事件名字將其說成單一任務完成 |
| `0x72` | `0x5033B0` | handler 本體不讀 quest ID | `QuestOwner+0x5EB0` WORD vector **end 回到 begin**，清空有效前置鍵，之後重建候選 | 不必然釋放 buffer、也沒有證明清空其後的 Server 資料庫 |
| **`0x74`** | **`0x503400`** | `WORD [pkt+2]` | 插入 WORD 到 `QuestOwner+0x5EB0..+0x5EB8` dynamic vector，然後 `0x500240` 重新評估候選 | **沒有先去重**；不是任務成功 ACK 本身；不是立刻顯示 Quest15 或給 Quest16 50 獎勵 |

上述皆為 **Client 在收到相應 application payload 時的條件式靜態反應**。原版 Server 是否、何時、對哪個玩家、回送哪一個，**沒有抓包／官方 Server 不可聲稱已證**。這與已證的 Client handler/dataflow 完成狀態分開。

### 0.1 原生 opcode→函式表定位（本段新增獨立閉合）

`0x5020B0` 在 `0xFAB2A4` 起的 table 按 **8 bytes per opcode** 初始化 default handler；下列各次 `mov [absolute], fn` 都直接來自 KR BIN，並由 `(absolute - 0xFAB2A4)/8` 算回 opcode，**不是根據名稱猜索引**：

| table 槽位 | table 絕對位址 | BIN writer | handler |
|---|---|---|---|
| `0x40` | `0xFAB4A4` | `0x5020CF` | `0x502270` |
| `0x45` | `0xFAB4CC` | `0x5020EB` | `0x5027D0`（獨立相鄰 handler，勿與 `0x40 state1` 混淆） |
| `0x64` | `0xFAB5C4` | `0x50211B` | `0x5030C0` |
| `0x65` | `0xFAB5CC` | `0x50212B` | `0x5035D0` |
| `0x6F` | `0xFAB61C` | `0x50213B` | `0x502170`（不同更新類型；本篇不以此取代 `0x74`） |
| `0x72` | `0xFAB634` | `0x50214B` | `0x5033B0` |
| **`0x74`** | **`0xFAB644`** | **`0x50215B`** | **`0x503400`** |

與 T16-122 界定一致：opcode 是這個入站 application handler 的索引；**非完整 TCP frame header**，framing/decode 邊界屬 T02。handler 中沒有讀到足夠資料時，不能從 `ret 0xC` 推定外層已驗證 payload 長度。

## 1. S2C `0x40`：state 0 / 1 / other 的實際 CFG

### 1.1 state==0 路徑（原生 BIN + 前段補證）

1. `0x50229E` 取得 packet pointer；`0x5022A1 mov eax,[ebx+4]`，`0x5022AC cmp eax,0`；非零跳 `0x5026CA`。
2. `0x5022F2..0x502313` 建構 `0x105B9` vptr `0xC467AC`，action `0xF4281`，`event+0x14` 來自 `DWORD[pkt+4]`（此分支是 0），入列 `0x58AA50`。
3. `0x502355..0x502377` **從 `WORD[pkt+2]` 零擴展 QuestID** 寫入另一個 `0x105B9` 事件 `+0x14`，action **`0xF438B`**，入列 `0x58AA50`。已在 T16-121 逐項閉合的 action table `0x5B7F80 → 0x5B6D20 → 0x636520(mode2)` 是**第二個事件**的消費者。若 packet ID=16 且任務資源／UI 條件成立，TalkBox `+0x80`=16、`+0x84`=giver10027、`+0x90`=2。
4. `0x50237C` 再讀 packet QuestID，呼叫 `0x500110`（在 `QuestOwner+0x5ED0` 的**20 WORD** 清單中若未命中，找空位插入；已存在則不重複；**滿20格可能不插入**）；`0x50238E..0x50239D` 以本地 selector `0x40F060()+0x8C` 呼叫 `0x500240` 重建候選。
5. 查 QuestInfo map `0x503D20`；若命中，依 `QuestRecord` 的 `+0x3C` type：type3→`0xF4306` 事件，type2→`0x422F40`/`0x561760` 控制器，其他→繼續後段位置／腳本／通知邏輯。這是**條件**，不能把所有 state0 訊息一律視為 quest UI 已開。

**重要 Client 語意**：`0x40 state0` 是 *event/UI/候選+exclusion 複合更新*；`0x74` 是 *prerequisite vector update*。兩者碰巧都可令候選改變，但存取的是不同 owner 欄位，不能合一。state0 即使派送 `F438B`，也不代表 Server 此時已完成 Quest16 或 award50。

### 1.2 state==1 路徑（本段原生確認）

`0x5026CA cmp eax,1`；其他值 `jne 0x5027AC` 結束。對等於1：

- `0x5026D3` `movzx edx,WORD [pkt+2]`，經 `QuestOwner+0x5EAC` QuestInfo map 和 `0x503D20` lookup；不存在 record 則 `0x5027AC` 返回。
- 若存在，`0x502708..0x502725` 取 record `+0x4C` small-string 大於等於8時 dereference heap ptr；這是一個**資源字串**，非 cache 中的新 quest-state 欄位。
- `0x502725` `push 0x12`，`0x5855B0 → 0x585330 → 0x4ED610 → 0x402250 → 0x40F8C0 → 0x4D6B30`，是文字/UI 派送鏈。此分支**不包含** `0x500110`、`0x500240`，也**不建構** `0xF438B` mode2 事件。故不能稱 state1 是 state0 的正/負 ACK 對偶，也不能因發出 UI 提示直接視為任務獎勵。
- state 1 沒有直接對 `QuestOwner+0x5EB0`、`+0x5ED0` 的 writer；同一 Client 可能還收到獨立的 `0x74`/`0x64`/其他訊息，必須按封包**各自套用**。

### 1.3 state 2、其他值、失敗／例外

`0x5026CD jne 0x5027AC`，即任何非 0/1 DWORD（含2）不進上列主功能路徑；handler return 0。不能以這個 default exit 推論官方 Server 用 2 表示「完成」、或一律拒絕。配置 event 失敗時，局部路徑可能仍呼叫 `0x58AA50(nullptr)`；後者 scheduler/佇列有自己的初始化及分派條件；不能用 static path 強保證 UI 真正顯示。

## 2. `0x74`：完成前置鍵的唯一已確認直接 writer，以及 0x72 重置

`0x503400` 使用 `ECX=QuestOwner`，`[EBP+8]` 是 packet pointer：

```asm
503403  mov eax,[ebp+8]
50340a  add eax,2             ; ptr to u16 payload key
50340d  lea edi,[esi+0x5eb0] ; begin/end/cap three DWORDs
503413  call 0x44b4e0       ; append one WORD by copying from eax
503418  call 0x40f060
50341d  mov eax,[eax+0x8c] ; local selector
503423  push eax
503424  push esi
503425  call 0x500240       ; rebuild candidate list
```

`0x44B4E0` 確切檢查 `begin<=inputPointer<end` 以應對來源與 vector 重疊；容量不足先呼叫 `0x44B5B0` 擴容，再用 `mov WORD [end],WORD [input]`、`end+=2`。**函式本身沒有掃描是否已存在**，因此重複 `0x74,QID16` 可在 Client vector 內形成兩筆相同前置 key。這是實際 parser/iterator 語義，不是原版 Server 冪等承諾。條件式相容 Server 應避免無故重複下發，但實際策略須以設計契約管理。

`0x5033B0`（entry index `0x72`）會計算 begin/end 的 byte count，將 end 設回 begin，再呼叫 `0x500240`。對動態 vector 來說**清空的是有效範圍**，不代表原本記憶體內容已覆零或堆記憶體已 free。

- `0x74, WORD16` 最少應用內容 bytes：`74 00 10 00`；受外層 decoder 的 framing/schema 限制，**不是通用 TCP 封包**。
- `0x72` 只由此 handler 觀察到空 vector/rebuild 效果，不得硬填 QuestID，亦不得從本體未讀任何 payload 就宣稱外層 packet frame 長度必為 2B。

## 3. `0x64/0x65`：exclusion 清除，而不是 prerequisite `0x74`

**單筆解除（`0x64`, `0x5030C0`）**：入口建構 `0xF4280` event，`0x503199 cmp [pkt+4],0` gate。state0 讀 `WORD[pkt+2]`，執行 `0x5000D0`：掃描 `QuestOwner+0x5ED0` 的**20 個 WORD**，命中置0，並呼叫 `0x53DC90` 更新其他本地對象；隨後 `0x5031AE..0x5031BB` 呼叫 `0x500240`。當 QuestInfo 資源存在時另透過 `0x5016F0 → 0x5536E0` 與通知物件走下游（UI 分支具有配置/資源/可用狀態門檻）。

**全表解除（`0x65`, `0x5035D0`）**：`0x503641..0x50369B` 建立 `0xF4280` 類事件；`0x5036A0` 判斷 `DWORD[pkt+2]==0`；state0 迴圈 20 次自 `+0x5ED0` 取 WORD，逐個呼叫 `0x53DC90`，再各自清零；`0x5036D4..0x5036E4` 呼叫 `0x500240`，後續建構通知物件。此 opcode **不能**當作「針對 Quest16 個別完成」，因為沒有逐 ID 選擇器而是批量 reset。

本段之原生證據支持：`0x40,state0` **加入** exclusion、`0x64,state0` **移除**特定 exclusion、`0x65,state0` **重置**全部 exclusion、`0x72` **重置**全部 prerequisite、`0x74` **加入** prerequisite key。這五個不同的「Client 狀態效果」各有獨立 handler。若 Server 把前置和排除欄位當成同一 set，就會在任務候選評估上錯誤。

## 4. `0x500240`：收到新旗標後怎樣影響 Quest16/Quest15

- `QuestOwner+0x5EAC` 是 QuestInfo map；`+0x5EB0/+0x5EB4/+0x5EB8` 是 prerequisite WORD vector begin/end/capacity；`+0x5EC0/+0x5EC4` 是候選 WORD vector begin/end；`+0x5ED0` 起 20×WORD exclusion slots。偏移相似 **不意味同一欄位**。
- `0x500240` 先將候選 vector 的 end 重置到 begin；依 world/context level 和 `selector=0x40F060()+0x8C` 掃 QuestInfo map，對每個 QuestRecord 依城鎮 selector、level、20-slot exclusion、全部 Demand keys 及資源條件判斷是否可加入候選。`0x5004C4..0x5004E7` 明確掃 `prerequisite begin..end` 比對 demand，`0x500110` 負責 20-slot exclusion 列表新鍵插入。
- 已知 Quest16 資源 `Demand14/type2/giver10027/town0`；故 key14 是 **Quest16 的一項必要條件**。在 Quest16 完成／後續 Server 自訂階段若收到 `0x74(16)`，Quest15 的 `Demand16` 可以通過這個 gate，但仍受 Quest15 town5、level、exclusion 及其他條件限制。**不保證立刻 UI 列出 Quest15，也不保證已獲 Quest16 獎勵。**
- **重要順序測試**：`0x72` 後只收到 `0x74(16)`，不代表 key14 仍在前置 vector；Server 若要在 snapshot 重建全部前置鍵，需正確考慮完整鍵集合及下發順序。這是 Client cache contract，不是猜測官方 Server transaction。

## 5. Quest16 在 `0x40` 下的玩家/UI 三情境矩陣

| 玩家/Server 訊息情境 | 必要 Client gate | Client 更新與 UI | C→S 後續 | 還缺甚麼 |
|---|---|---|---|---|
| NPC10027 的 type2 候選可得（T16-121） | key14、town0、level及 exclusion 等一致 | controller local QID16；本身不代表入站 UI | 前段 T16-122 可有 `0x1C` actor payload / deferred `0x3F` | 原版 Server 哪個 request 對哪個 response，不能由 Client 單向 code 靜態推斷 |
