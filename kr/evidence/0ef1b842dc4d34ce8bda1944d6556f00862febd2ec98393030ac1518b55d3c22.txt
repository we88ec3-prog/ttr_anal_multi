# 原版韓版任務通知與狀態更新邊界

本輪只分析 `Tartaros.bin`。沒有啟動服務、附加遊戲、修改封包、資源、存檔或 v41 AI。可重跑 `anal/audit_quest_state_notifications.py`；輸出為 `anal/native-index/quest-state-notifications-audit.json` 與 12 份完整範圍反組譯。SHA、指令覆蓋、內部分支邊界、RTTI、註冊位置及關鍵指令檢查均通過。

## 已確認的任務 ID 來源

`40F930` 返回全域 `FAB2A0`；初始化函式 `4FFE60` 安裝 `CQuestMgr` 的 vtable `C0DB08`。任務記錄容器位於 manager `+5EAC`，即全域 `FB114C`。

`500F90` 依輸入 ID 查找這個容器，返回 node `+10` 的記錄。前輪對話框 `+88` 保存的就是這種記錄；確認時 `C2S0036` 使用記錄起始 WORD，封包總長 4 bytes。這不表示伺服器會回傳同號命令。

`500950` 遍歷 manager `+5EC0/+5EC4` 的 WORD ID 清單，查找記錄，要求記錄 `+28` 符合輸入 context 且 `+4==1`。`5007D0` 再搜尋記錄 `+10/+14` 的 DWORD 清單是否包含輸入 ID，符合時回傳記錄起始 WORD。這是前輪 mode 3 → `F438A` 對話事件所選 ID 的來源。

## 接收端註冊與效果

`5020B0` 初始化 manager 的每個 8-byte handler/metadata slot；`4FDA30` 以 signed WORD command 取 `manager+command*8+4`，再呼叫處理函式。已確認専用註冊命令為 `0040/0045/0046/0047/0064/0065/006F/0072/0074`。這張表沒有為 `0036` 寫入專用函式；此結論只限這張表。

以下 offset 均從封包 command WORD 開始計算；長度是已讀欄位所需下限，未經正式流量確認為完整固定長度。

| S2C 命令 | 原版函式 | 已確認欄位 | 完整函式內可見效果 |
|---|---|---|---|
| `0045` | `5027D0..502B3F` | signed WORD `+2`，至少 4 bytes | 依 ID 查記錄；記錄 `+44==3` 發 `F4306`、資料取 `+40`；`+44==2` 呼叫 `561760`。其他分支使用 `QUEST_READY` 與記錄名稱建立 UI 物件／文字通知。 |
| `0046` | `502B40..50303B` | signed WORD ID `+2`、WORD result `+4`，至少 6 bytes | 所有結果先排入 `F4282`；result 0 才清除匹配的 20 格 ID、在記錄 `+8!=3` 時將 ID 傳給 `+5EB0` 的清單 helper、重新計算 `+5EC0`，並發 `F438C`。result 1..5 走其他提示分支。 |
| `0064` | `5030C0..5033A6` | signed WORD ID `+2`、DWORD result `+4`，至少 8 bytes | 先排入 `F4280`；result 0 清除匹配的 20 格 ID、重算 `+5EC0` 並建立 UI 通知。非 0 返回 `80004005`。 |

`0045` 是通知顯示路径，不能只因畫面顯示完成就推定本地清單已推進；`0046/0064` 有明確的結果檢查與清單更新。尚未確認它們的官方命令名稱、結果枚舉或與 `0036` 的正式回覆順序。頂層接收分派如何將封包送入 `CQuestMgr` 也不屬於本輪完整審計範圍。

## 可用任務清單的重算

`5000D0..50010B` 搜尋 manager `+5ED0` 起的 **20 個 WORD 槽位**，找到相同 ID 就清為 0，並呼叫 `53DC90`。**它不刪除 `+5EAC` 的任務定義記錄。**

完整 `500240..5007CA` 先清空 `+5EC0` 清單，再遍歷任務記錄，篩選條件包括：

- 記錄 `+20` 必須符合輸入 context；記錄 `+C` 與從角色資料彙整出的數值比較。該數值的正式名稱未核定。
- ID 不可已存在於 20 個 WORD 槽位，也不可已存在 `+5EB0` 清單。
- 記錄 `+10/+14` 所列 DWORD ID 必須都能在 `+5EB0` 清單找到，才加入 `+5EC0`。
- 另有全域容器 `FB9398` 的排除檢查；其資料來源與正式用途尚未完整展开。

因此 `+5EB0` 同時參與排除與前置條件檢查，可能是歷史進度集合，但目前保留欄位名，不將它直接命名為「已完成任務」。對話候選清單也會受到這些條件影響，並非單純顯示下一筆文字。

## 與怪物觸發追查的關係

這 12 個完整函式沒有直接呼叫已知 `CMonster` 建構函式 `4D1710`。其 UI 事件消費者、helper 與間接呼叫尚未窮盡，所以不能推論任務更新絕不影響地圖事件。

目前已將 checkpoint → 對話確認 → 任務候選清單更新分開。下一步優先核對 `F438C` 等更新事件是否只重整 UI，並追查頂層任務通知的送達路徑；若仍沒有怪物生成呼叫，就回到普通怪物行動訊息的產生端，避免把文字通知誤當 AI 啟動訊息。原版區域／波次排程、怪物 AI 決策來源與 P2P 權限仍未確認。
