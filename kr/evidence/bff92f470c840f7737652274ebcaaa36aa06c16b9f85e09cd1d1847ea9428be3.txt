只做原版韓版 `Tartaros.bin` 靜態分析。沒有啟動服務或遊戲，沒有修改資源、存檔、封包或 AI。執行 `anal/audit_quest_followup_delivery.py` 可重現；5 個完整函式及註冊／事件映射檢查通過，詳見 `anal/native-index/quest-followup-delivery-audit.json`。

## 任務通知確實有獨立接收路徑

本輪重新由完整 `493170..494354` 註冊函式解析 CClient 表，與既有 `CLIENT-MANAGER-AND-PARTY-ROUTES.md` 交叉核對：

`0040/0045/0046/0047/0064/0065/006F/0072/0074` 都送入 `494440..4944C1`，由它呼叫 `FAB2A0` 的 virtual `+4`，即 `CQuestMgr` 共用分派函式 `4FDA30`，再查各命令處理函式。

上游完整 `48AAD0..48AB67` 使用 16-byte 命令槽。不能使用原場景的 `mainPacketHandlers` 清單推定這些命令不存在，也不能將所有任務通知當成場景封包。這是對既有送達路徑的重新核對，不是新發現另一種傳輸方式。

## `F438C` 會開啟後續对話

前輪已確認 `S2C0046` 的 result 0 分支更新進度清單並發出 `F438C`。本輪確認原版 Lobby／Square 事件表的 `F438C` 分支為 `5B8011 → 5B6E60`。

完整 `5B6E60..5B6F94`：

1. 要求事件型別 getter 為 `105B9`，取 event `+14` 作為任務 ID。
2. 在 `FB114C` 的任務記錄容器查找該 ID；找不到就返回。
3. 呼叫 `636520`，對話框為 page `+224`，data ID 取任務記錄 `+2C`，context 取全域 `FAB1BC`，mode 設為 **3**，第三個堆疊參數仍是 event 的任務 ID。
4. 透過 `74A010/596E00` 走既有 UI 顯示路徑。

第三個堆疊參數十分重要：initializer `6366CE` 讀 stack `+10`，交給 `500F90` 查任務記錄並存入對話框 `+88`。它沒有將 data ID 誤用為任務記錄 ID。mode 3 取該記錄 `+38` 的文字鏈。

結合前輪完整函式，後續鏈為：

`0046/result0 → 更新清單 → F438C → mode3對話 → 5007D0選下一筆 → F438A → mode1對話／確認 → C2S0036`

選下一筆時，`500950` 要求候選記錄 `+28` 等於目前對話 data ID（即先前記錄 `+2C`），且候選 `+4==1`；`5007D0` 再要求其 DWORD ID 清單含有目前 `+88` 記錄的起始 ID。沒有符合候選，就不發 `F438A`。因此任務更新後未出現下一段對話，不能只檢查通知是否送出，也必須檢查候選清單與記錄間的連結。

這是靜態條件鏈，未取得原官方封包順序或目前遊戲頁面快照。不能把原版 Lobby／Square 接收方式套用到所有頁面；此前 TutorialField 的同類事件分派仍屬另一條路徑。

## 相邻事件 `F438B` 的差異

事件表 `F438B → 5B7FFF → 5B6D20`。完整 `5B6D20..5B6E54` 同樣使用 event `+14` 找任務記錄，但 data ID 取記錄 `+28`、mode 為 **2**；initializer 取記錄 `+34` 的文字鏈。

既有完整 `636B70` 的尾段只在 mode 3 選下一筆，mode 2 不走該分支。不能因兩個事件都開對話，就將它們當成相同的任務推進機制。本輪未完整擴充 `0040` 的所有產生分支，不替 `F438B` 指派官方名稱。
