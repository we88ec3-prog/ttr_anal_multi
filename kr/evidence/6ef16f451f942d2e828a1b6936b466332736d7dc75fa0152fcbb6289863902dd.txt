# 韓版怪物生成、操控分配與地圖標記的邊界

本輪只分析原版 `Tartaros.bin`，未變更服務、主程式、存檔或正在執行的遊戲。部署中的 v41 怪物 AI 仍是自製版本，尚未啟用原版怪物決策。可重跑 `audit_monster_spawn_control.py`；8 個函式的反組譯、分支目標、封包登錄與關鍵指令檢查已通過。

## 1. 生成並不等於啟動自主控制

`S→C 0007` 的完整接收路徑為 `4AE4D0`。正常返回在 `4AED80`，但還有 `4AED83` 的失敗分支；本輪保留該分支，並將 `4AED90` 起的八項跳轉表當作資料，避免混入下一個函式。

封包前置 2 bytes，每筆 26 bytes。以下 offset 相對於單筆資料：

| Offset | 格式 | 已確認用途 |
|---|---|---|
| 0 | WORD | actor ID；低位元組選擇生成類型 |
| 2 | BYTE | 參與資源索引的第二欄，計算時減一；實際語意尚未命名 |
| 4 | WORD | 模型／資源編號，參與資源索引 |
| 6、10 | float | 初始平面座標，交給 actor virtual `+44` |
| 14 | float | 交給 actor virtual `+5C` 的係數；本輪未重追完整 callee |
| 18 | DWORD | 寫入 actor `+9C` 的擁有者資料 |
| 22 | BYTE | 朝向，交給 virtual `+58` |
| 23 | BYTE | 類型附加資料；怪物寫入 `+424`，值 4 亦影響 `+428` |
| 24 | BYTE | actor `+90` 陣營 |
| 25 | BYTE | 狀態元件 virtual `+8` 的輸入 |

低位元組 1 的分支呼叫 `4D1710` 建立 `CMonster`，再設定位置、朝向、模型並加入共用物件表。**擁有者非零的分支只嘗試補玩家紀錄中的目前 actor，並未在此呼叫三槽控制器登錄。** 同一欄位在其他路徑的作用仍需分別判定，不能直接稱為怪物 AI 主機權限。

共用登錄 `4DFF30..4DFFA9` 以 actor `WORD +4` 為 key，將物件指標加入 GameInfo `+8` map。`4C6E50..4C6E9C` 則寫玩家紀錄 `+4` 目前 actor ID、`+8` 模型 ID。這兩個函式本身沒有建立決策 AI；相關容器 helper 尚未逐一展開。

原始索引列出 `4DFF30` 的五個直接呼叫候選：`4A11B6 / 4AA222 / 4AEC03 / 4AF4F7 / 4B2F83`。其中 Lua 生成、0007 生成與掉落物接收路徑已定位，其餘仍須核對完整 caller，不能把這份候選表當作完整呼叫圖。

另一生成分支 `4D1060` 的 RTTI 是 **CEventObject**，不是 CMonster；該物件 `+420` 的資料不可與怪物的速度基準鎖存 `+420` 混用。

## 2. 000A 分配的是既有控制器，不是已證實的怪物 AI 接管

完整接收函式 `4AF920..4AFAE7`：前置 7 bytes，包括 offset 2 的 owner DWORD、offset 6 的 signed BYTE 筆數；每筆 4 bytes 為 actor WORD 與 related actor WORD。

先以 owner 查 GameInfo `+18` 玩家表，再與本機玩家 ID 比較。本機分支會重置控制器，接著：

- actor 與 related 不同：呼叫控制器 virtual `+8`，加入先前確認的額外跟隨記錄。
- 一般分支：首筆標記 actor `+98=1`，更新玩家目前 actor；後續筆 `+98=0`。寫入 actor `+9C=owner`，本機分支呼叫 virtual `+4` 登錄主要槽位。
- 最後本機分支呼叫 virtual `+10` 完成設定。

接收函式沒有模型 `<=9` 限制，因此不能說怪物絕對無法被登錄；但已追到的主要輸入／隊友 AI 消費端有角色模型限制。**目前沒有證據顯示普通怪物透過此封包取得自己的決策控制器。** 使用者提出三槽可能供斷線隊友 AI 接管，是合理待查假說；這個函式尚未證明斷線觸發條件。

Lua `CreateObjectEx` 的第六個非零參數也走控制器 virtual `+4 / +10`。這不是另一個已確認的怪物專用 AI 開關。

## 3. 怪物生成時額外建立的 72 bytes 是地圖標記路徑

怪物分支 `4AE69D` 配置 `0x48=72 bytes`，寫 kind 7、初始 actor ID、座標、顯示狀態與文字，再由 `4AE77A→56F5C0` 加入全域 `FDF3C4` 管理器。

本輪追到完整消費鏈：

1. 初始化視窗 `48D4D2..48D504` 配置 `0x84` bytes，呼叫 `56DE30`，把結果存入 `FDF3C4`。此處只有局部初始化證據，未將整個上層大函式宣稱為完成分析。
2. 完整建構函式 `56DE30..56E0AB` 建立 `+54` 串列，並以原版 UTF-16 名稱 **`MinimapCached`** 建立 `+60` 快取。
3. `56F5C0..56F728` 依 kind 與 actor ID 合併／加入串列記錄；重複記錄釋放走 `56F0F0..56F121`。
4. 完整消費函式 `56F130..56F5B5` 讀取記錄座標、轉成繪製位置、呼叫 `739230`，並經 `735BA0` 繪製文字。`56F830` 另複製 `+74` 座標集合。

這提供了它負責地圖圖示／標記的具體證據，**不能把加入這個串列視為加入怪物 AI 排程**。渲染 helper 並未全部展開，這也不代表整個客戶端不存在其他怪物 AI。

## 後續分析入口

目前已拆開「生成共用 actor」「玩家操控分配」「小地圖標記」「收到命令後的原生移動」四條路徑。下一步應追普通戰鬥的怪物移動／技能命令產生端，以及尚未核對的生成 caller；同時保留可能的獨立 P2P／權限分配路徑。速度 CC、倍率 D0、陣營的初始化是必要檢查，但補速度不等於找到自主 AI。
