## CSquare 初始化與玩家資料保留邊界

原生 vtable：+4=`4C4670`（訊息分派），+10=`4BBC10`（初始化），+14=`4BBF10`（退出），+2C=`4B2570`（ready）。

`4BBBA0` 將 scene+5EAC 的第二層 handler table 清零，只覆寫 command 1F/25/68/6A/6B；沒有覆寫 12/14。`4C4670` 在第二層槽為零時走 `4FDA30` 的基底表，基底 constructor `4ADD50` 在 +94/+A4 分別登記 `4B24F0/4C5930`（`4ADE41/4ADE51`）。所以本次 reset／ready 確實可由 CSquare 基底接收，不能只引用另一場景的相同函式。

初始化局部行為（`4BBC10..4BBF08`）：先做 UI helper、目前 controller virtual+14；`4D...` manager 的清理 `4DFE90(FAB130)` 會遍歷其 +C 樹內 value 物件，virtual+14、virtual+0(1)，清樹後再呼叫 controller virtual+14；之後 `FAB228=0`、`4E1070(FAB148)` 釋放另一樹內值。僅描述已追到的容器，不宣稱覆蓋全部 actor／玩家初值。

控制器重用條件在 `4BBD36..4BBDA8`：當 `FBA7A4 != 0 && FBA7AC==2` 時呼叫 `544F50` 並跳過 constructor；不同種類則 virtual+28、可用時 virtual+0(1)，分配 C0 bytes、呼叫 `548540`、安裝 FBA7A4 並 virtual+24。`548577` 寫 C0FAC4，RTTI 為 `CSingleController`，`5485D6` 寫 kind=2。這裡 kind 是控制器種類，非房主／玩家號碼。

| 範圍 | 明確清理／保留 | 限制 |
|---|---|---|
| CSquare 開始初始化時的現 controller virtual+14 | 已知 Single 指向 `545210`：清三槽指標與旗標、額外 +30/+34 向量收空 | 其他種類 virtual 實作未重做；只以當前動態類型分派。 |

## 0012 reset 的更正與 Map 介面

舊 [SCENE-ENTRY-RESET-AND-READY 保存報告](../../kr/evidence/0bab714e82d96b0f6a4165471fc52531ba4b250f63878e2721bdd706fb8bab37.txt) 將 FB79F0 稱為 actor manager，並推論先前 managed actors 被清除。本輪查原始 `4B250D` 寫 vtable C0F868，COL C6C534 → type descriptor F7F514 → `.?AVCCheckPointMgr@@`。`5449A0..5449FE` 只證明遍歷該容器 +4/+8，對每筆 virtual+14／virtual+0(1)，最後 end=begin。**此處更正的是泛化名稱與「全部 actor」推論範圍；不推翻清理迴圈本身，也不反向保證 actor 存活。** 保留舊證據，正式報告未覆寫。

`544F50..545039`：清 controller+5C/+60/+40/+44、+64=timeGetTime、FBAB48=1；對三槽 virtual+1C(i) 做資源解除，再清 +0C/+10、+18/+1C、+24/+28，將 +14/+20/+2C 的 byte 旗標設為1。保留物件本體／vtable，不在此直接重建控制器。

## ready 與初始化0043的區別

CSquare ready `0014 → 4C5930 → [scene.vtable+2C]=4B2570`；`4B2593..4B259D` 直接取得 FBA7A4、寫 +4=1。接著是 UI/global flag 分支，FB73E8==0 時清 FB8830 bit0，return0。沒有 controller null guard；沒有檢查 Map182/183、模型／BOUND載入成功、玩家已生成或綁定。有限函式內無直接 sender，不宣稱所有 helper／未來 tick 均不發包。

另外，CSquare **初始化**在 `4BBE59..4BBEAF` 取得 `[FE1AA0]+18` 的低 byte，建立本體 `43 00 xx 0A`，若 FBA798==0 就呼叫 `[FBA854].virtual+10(0, buffer, 4)`。這是原生 outbound callsite；不在本輪重做 T03 framing，也不將 channel參數0命名成後端業務語意。

該0043路徑發生於0069處理器的同步安裝期間，**早於這一份0069更新 F9392C 與 `[FE1A88]+18/+1C`**。沒有證據支持它就是0014的ack、地圖已載入回覆，或一定形成 `0042 → 0043/0069` 的官方 request/reply 關係。

## 順序約束與後續開發

工具觀察給出同步局部順序：0069分支建構 → install（退出舊場景→安裝新場景→CSquare init→可能0043）→分支mode欄位→0069尾欄位；0012內則 checkpoint容器清理→controller reset→map selector處理。0014操作當前場景／控制器，而非預先指定的目標城鎮。

分析者推論：要讓新玩家綁定保留下來，後端重建流程應避免在完成綁定後又進入上述會清槽的場景初始化／0012；綁定應對應最後有效的場景與reset世代。此為由清理副作用導出的開發約束，**不是官方完整發包序列**。也不能推出「先0012後0014」是唯一官方排序；尤其0012沒有直接清+4。

待補資訊與主責：

1. 0069 type7/23/24的官方模式含義、尾byte合法值、兩村正常進入時是否都使用CSquare：T07仍缺伺服器／原生其他使用點的直接映射證據；本輪不指定其中一值為兩村通用值。
2. Town1/2 context 與 Map182/183 正常配對：沿用T06候選與限制；不能將0069尾byte或0043低byte自動作此對照。
3. 玩家綁定與重置後重新送資料：T08/T04介面仍需補齊；T09提供合法spawn/bounds。場景／controller型別這一項依賴已可引用，不代表所有切城阻塞解除。
4. 後端需明確設計切城交易、舊世代訊息處理、相同selector重試、失敗回復、party／return政策；屬重建開發項，不冒充原版規則。沒有部署或改服務。
5. 本次靜態資料不能驗收實際資源載入、玩家操作或完整官方時序；既有禁止執行／附加限制維持。
