# 地面掉落與 Space 撿取

狀態為 S00 離線分析與 Server 擊殺、掉落、撿取入包合成測試。正式掉落表與實機驗收待完成。此項開發沿用目前的戰鬥流程，地圖與怪物 MEF 分析暫停。

## KR Client 讀取的地面道具

來源為 KR 原件 `Tartaros.bin`，SHA-256 `9741d1975327b9309d82b52f631165bc410757694d7c183a5eed970a53ebef91`。程式位置使用 VA，對照檔案位移時減去 `0x400C00`。

S2C `0021` 的入口在 `0x4ADECD` 登記至 `0x4B2CD0`。函式按 `(payloadBytes - 2) / 31` 讀取資料列（`0x4B2D44–0x4B2D77`），從 opcode 後第一個位元組開始，以 31 bytes 為步長建立 `CDropItem`（`0x4B2EB9–0x4B2F52`、`0x4B301B`）。欄位均為 little-endian。

| 列內位移 | 型別 | 已確認行為 |
|---|---|---|
| 0 | u16 | 地面物件 ID。Space 搜尋接受低位元組為 3 的物件 |
| 2 | u16 | 外觀選擇值。建立時與 `0x03000000` 做 OR，對應 `_ActorList.xml` 的類別 3 |
| 4 | 2 bytes | 此處理函式未讀取，合成封包填零 |
| 6、10 | f32、f32 | 起始 X、Y |
| 14、18 | f32、f32 | 落點 X、Y |
| 22 | u32 | 非零時設物件 `+0xF4`，用途待核對 |
| 26 | u32 | Product ID，寫入物件 `+0x11C`。後續在 `0x4D0A10` 使用 Product 表 |
| 30 | u8 | 數量，後續由 `0x45F1B0` 讀取 |

S2C `001A` 可按同一 ID 移除地面物件。入口 `0x4B28D0` 在 `0x4B2AB5–0x4B2AC7` 呼叫物件管理器 `0x4DFBC0`。Server 可沿用現有六位元組移除封包。

`CDropItem` 的 `0x4D014C–0x4D015D` 用物件 `+0x88` 查 actor 表，`0x4D0162–0x4D01AB` 取檔名並加上 `.eff`。韓版 `_ActorList.xml`（SHA-256 `b01ae70817c79126b89292567e32d4c806c3ef31478b6a2eb96dcfd21e2c78f7`）的類別 3 有 ID 162、`Spell_Scroll01`、普通復活卷軸。韓版 `Product.xml`（SHA-256 `8c9262f81ca4dae6b62be5d3373bd06d6e96e7470b4227fc73c98fda4e88457c`）的 Product 183 指向同名 Item 183。測試採用這組外觀與 Product，兩者以各自欄位傳送。

原件及工作目錄的 `Effect/Effect.stp` 索引均有 4,281 個成員，沒有 `Spell_Scroll01.eff`。`Effect/Effect.stp` 原件 SHA-256 為 `ef0c4fae74c5660aaea7cbe0919549c20db2fd248c81f829aeb7616a11b300ec`。依檔名比對原件類別 3 的 343 筆資料，只有貨幣 ID 1 對到該封裝的 `Effect/Assist/State/S_Item-Money01.eff`。`0x4D01F1–0x4D01F9` 在效果查找為空時跳到 `0x4D02C0`，仍繼續物件狀態初始化。這支持物件可能可撿但缺少地面特效的待測項目。一般道具的實機可見性與其他載體仍待確認，正式表先不啟用。

## Space 的請求與後續接線

- [T10 輸入契約](../../kr-temp-roy/T10/20261103-T10-T11-KR-INPUT-CONTRACT/input-contract.md) 將邏輯輸入 23 對應為 Space。`0x49C74F–0x49C77D` 處理按下階段，`0x49CE10` 搜尋鄰近候選。`0x49CEF0–0x49CF62` 檢查物件類別、條件式檢查 Product 並比較位置。
- Client 的候選搜尋判斷是 `dx² + dy² < (actor[+0xB4] × scale)² + 100`。`0x49CE9F–0x49CEB3` 取縮放後的值，`0x49CF3C–0x49CF62` 完成平方與比較。`0x54F979–0x54F986` 將預設 `float 0.09` 寫到縮放全域 `0xFB90BC`，加數來自 `0xC557E8` 的 `double 100`。角色欄位與設定覆寫仍須核對，固定 Server 半徑尚未定案。
- `0x44481F–0x44482F` 寫入 C2S `0007`，`0x4448B5–0x4448BE` 對 Space 將第三個位元組設上 `0x80`，`0x4448DC–0x4448E4` 送出三位元組 payload。`0x548888–0x5488A6` 與 `0x5489B9–0x5489EC` 提供另一條相同長度的路徑。封包沒有目標物件 ID，且第三個位元組可同時含其他輸入旗標。
- Server 依目前單人主線場景及權威位置選取半徑內最近的掉落。成功入包才發布背包更新及 `001A`。背包滿或交易拒絕時保留物件。首次撿取沿用 `0029` 初始化和 `002C` 餘額快照，後續以 `002C` 更新單格。畫面是否正確更新仍待實機確認。
- 掉落表使用 `.ground-loot.json` 與[獨立 schema](local-ground-loot.schema.json)。一筆規則以 `quest / map / monster` 唯一鍵對應擊殺時的單筆必掉物品。半徑、數量與外觀由設定提供。堆疊類物品的 metadata 必須和同 Product 的既有堆疊一致。Server 啟動時以 `TARTAROS_LOCAL_GROUND_LOOT_PATH` 及 `TARTAROS_LOCAL_GROUND_LOOT_SHA256` 載入，並核對主線關卡、怪物配置與背包儲存。進度跳轉測試與教學首戰未接入此規則。

## 馮德斯一般副本 Stage 1

本機 Server 可用 `TARTAROS_LOCAL_STAGE_ONE_BOSS_DROP=REVIVAL_SCROLL` 啟用頭目掉落。這項 Server 規則在 Case 1 終點地圖 19 的頭目 1086 被擊倒時，建立一張 Product 183，使用上述類別 3 外觀 162。堆疊 metadata 沿用馮德斯雜貨店的同商品設定。頭目 ID 參考 [Case 與群組分析](../../governance/s00-iterations/S00-20261101-MEF-RECEIVE-FEASIBILITY.md)，獎勵品項、必掉一張及拾取半徑 12 均為本機驗收設定。

正常進場才配置掉落。玩家在清怪後、按出口前，可用 Space 撿取，沿用租約、背包與掉落 GUID 的同交易入帳。出口確認後結算經驗，換圖或結算會釋放當前地面清單。進度指定場維持零道具及零經驗。實機批次需確認頭目倒地後能在落點撿取、背包增加一張、再走出口完成通關。外觀效果與原生 `.mef` 接收仍待確認。

Stage 1 的掉落由 `.scenario.json` 的節點 `groundDrop` 提供，包含怪物模型、地面外觀、商品、數量與拾取半徑。綁定的模型和 PRE 須出現在該節點的初始怪物或增援中。Case 1 的節點 2 使用 `{"monster":1086,"visual":162,"product":183,"quantity":1,"pickupRadius":12}`，含通關經驗預設值的關卡檔 SHA-256 為 `baa48fb43ec35420167be093e331c74fb2cbc0590da720f0626898ff2c6f64d2`。主線掉落沿用原有掉落表。 [關卡 JSON schema](local-scenario-definition.schema.json)

Host 可用 `TARTAROS_LOCAL_STAGE_ONE_BOSS_DROP=SCENARIO_CATALOG` 啟用關卡內配置的商品。每項 Product 必須在已載入的商店資料中有一致且完整的背包 metadata，啟動時即核對。裝備每筆只掉一件，撿取沿用共用的獨立裝備實例與背包交易。原 `REVIVAL_SCROLL` 模式仍支援 Product 183。正式 Case 1 維持復活卷軸，其他商品的地面外觀及實機撿取另驗。

一般副本啟用掉落後，載入關卡時會比對單筆掉落數量與撿取交易使用的堆疊上限。若同一 Product 有多家商店，兩處均取最小值。單筆掉落若連空背包都無法收下，Host 會回報商品和上限並停止載入。實際撿取仍須核對既有堆疊數量及可用格位。

在 `SCENARIO_CATALOG` 模式，若商品表的 Product 183 列省略 metadata，沿用商店購買同商品時使用的 `TARTAROS_LOCAL_TOWN_TRADE_ITEM183_FIELD10`／`TARTAROS_LOCAL_TOWN_TRADE_ITEM183_FIELD14`。先補值，再比較該商品各店的實際入包欄位。商品表須有該 Product，所有列的實際欄位須一致。其他商品仍使用各自商品列提供的 metadata。

再次核對韓版 `Product.xml`、`ItemTable2.xml`、`ItemUsableTable.xml` 的 183 對應列。商品表提供 Product → Item 對應、價格及商品旗標。道具表提供 class 26、堆疊上限 100、gettype 3、冷卻群 2，使用表提供兩個動作條件。這些列尚無可直接對應背包 `+10h`／`+14h` 的資料來源，部署仍使用明示的兩個欄位。 [背包接收欄位](../../governance/client-variants/20261109-mef-town-services/shop-asset-sync.md)

正常入口的合成驗收使用測試商店目錄提供 Product 2614 的背包欄位。由廣場建隊、進村後連打兩場，每場擊倒頭目後送 Space 撿取，核對掉落商品、背包初始化列及地面物件移除。兩場結算並回村後，SQLite 有兩個不同 ID 的裝備實例，各一件，經驗也各自入帳。測試欄位值與地面外觀為合成設定。

一般副本換圖、進結算或離隊回村時，Server 會先以既有 `001A` 清除原圖尚未撿取的地面物件，再結束該圖的掉落狀態。已撿取物品留在背包，結算時不會重送其地面移除。合成驗收核對首圖未撿的三件掉落在換圖前移除，以及頭目掉落保留在地面和先撿取兩種結算順序。指定 v2 的畫面仍待驗收。

一般副本的 `groundDrop.pre` 預設為 1。Server 載入關卡時會檢查該節點的初始怪物或增援有相同的模型與 PRE，擊倒時依這兩欄決定是否掉落。Case 1 的復活卷軸因此綁定 `1086/PRE1`。這是 Server 關卡規則，原服掉落與指定 v2 實機呈現仍待驗證。

節點可改用 `groundDrops` 配置 1～16 筆，不與單筆 `groundDrop` 同時使用。依初始怪物與增援計算的整圖掉落總數上限為 255。一次擊倒可發出含多筆記錄的 `0021`。每筆有自己的地面物件、拾取半徑與持久化領取 ID。Space 依可到達的距離順序嘗試拾取，同距離依生成順序。一筆成功即停止；堆疊已滿的物品留在地面，其他可入包物品仍能撿取。正式 Case 1 配置一張復活卷軸，合成測試配置 Product 2614 和 183 同場掉落，驗證卷軸已滿的第二輪仍可取得裝備。這些規則屬於 Server 關卡格式 `NOT_NATIVE_MEF`。指定 v2 對多筆同時掉落的畫面與拾取仍待驗收。

## S00 GAME_RUNTIME_OBSERVATION：撿取入包

一般及主線副本的關卡掉落可指定 `waveId`，只套用於該節點同名的順序或定時增援。省略此欄時，所有同模型與 PRE 的怪物沿用既有規則。載入時會核對目標波次、怪物與整圖掉落上限。同模型、PRE 及 Product 可分別配置在不同波次，避免與未限定波次的規則重疊。

Case 693 地圖 3431 有兩隻初始怪與第三隻順序增援，皆為 1022/PRE1。這份 Server 驗收配置只讓增援掉一張 Product 183。原版地形離線流程驗證該圖只生成一張，能用 Space 拾取，回村後 Case 693 合計三張卷軸、76 EXP。指定 v2 的地面顯示與實際拾取仍待驗。

編譯主線關卡圖時，沒有指定波次的掉落會省略 `waveId`，使既有內容的序列化與雜湊維持相容。部署已核對 Q119 關卡圖仍為 `f792b3ced0636cb3fea08f52ec985eaf4c5410888519ebf84c34bed84ef70fcd`。Case 693 的出口 6 路線另外在原版地形驗到地圖 3435，首圖、增援及頭目三筆卷軸皆入包，合計 76 EXP。新版已部署到本機 v2 驗收 Host。

馮德斯 Case 693–696 的八條分支均已離線核對 `0021` 的 Product、外觀欄與數量。以原版 BND 檢查每個實際落點與玩家出生點位於同一可達區域，並在離落點約 6 單位且路徑暢通的位置送出 Space 請求。確認道具入包、地面物件移除與結算。指定 v2 的可見性、Space 搜尋範圍與操作仍由 TS-37G 實機核對。

1. 地面掉落建立時分配全域唯一的 Server 掉落 ID。每張圖對 Client 發送的 16-bit 物件 ID 用於建立和移除，允許在不同場次重用。
2. 以有效的冒險團連線租約寫入既有背包的 100 個可寫入格位。堆疊類每 Product 一疊，撿取時以已載入的同商品商店上限為準。多家商店上限不一致時取最小值，沒有商店記錄時沿用 255。若整筆掉落加上原有堆疊後會超過上限，物品留在地面。既有堆疊可照常使用或售出。獨立商品每筆掉落數量須為 1，每筆使用空格，並將掉落 GUID 保存為物品實例 ID。首次撿取且沒有錢包資料時，隨交易建立餘額為零的錢包，供商店及倉庫共用。 [獨立商品來源及身分](PHINDOS-EQUIPMENT.md)
3. 同一筆交易寫入背包與掉落領取記錄。需要首次背包初始化時，交易成功後回傳含新物品的完整背包快照，再依序發布 `0029`、`002C`、`001A`。後續撿取沿用單格更新。場景若在提交後重試同一個掉落，僅接受同一帳號、Product 和數量。堆疊類回傳目前的堆疊。獨立物品只回傳該 GUID 對應的背包格，已存入倉庫或賣出時沒有對應的單格更新，仍可回傳目前背包快照。
4. 沿用 SQLite 商店／背包元件 V6，無需新的資料庫升級。清場後若同一張圖重建出口，重送尚未拾取的地面物件，並保留領取識別。換圖後新的場景有自己的掉落清單。掉落領取記錄的清理須等場景重送期限與 ID 生命週期有明確規格。
5. 合成測試涵蓋堆疊類與獨立物品。獨立物品案例以兩隻測試怪各掉一件 Product 2614，驗證兩個地面物件、不同背包格、存入倉庫與取回，以及指定格售回後另一件仍保留。合成外觀採類別 3 的 ID 7，實機可見性仍待確認。 [批次驗收 TS-12](../testing/S00-CONTENT-BATCH-TESTS.md)

主線副本換圖或進結算時也先發送 `001A`，清除離開地圖前仍在地面的道具。同一張圖在清場劇情後重建出口時，會重新發布原有 `0021`，保留物件 ID 和領取狀態。Q119 正常入口的合成案例已核對掉落在劇情後重新發布，並於最終出口先移除再送結算。指定 v2 的地面顯示仍待實機。

主線外部關卡檔可直接設定節點掉落。同節點有設定時，以關卡檔為準；其他節點沿用舊掉落表。正常入口的合成測試分別核對舊表一張卷軸及節點覆蓋後兩張卷軸，兩種設定皆在劇情後重發同一筆掉落並於結算前移除。 [Q119 範例與設定](STORY-SCENARIO-OVERRIDES.md#關卡內的頭目與掉落)

Q119 合成案例也驗證從正常進村開始，擊倒關卡指定的必要頭目，清場劇情後以玩家位置選取可達的掉落，並交由共用背包交易撿取。背包初始化及重開的 SQLite store 都讀到兩張 Product 183，已拾取的物件在結算時不再發送移除。此案例使用合成地圖與道具數量；指定 v2 的 Space 操作及正式四圖範例仍待實機。
