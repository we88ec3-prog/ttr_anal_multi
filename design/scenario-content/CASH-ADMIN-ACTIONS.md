# 商城補發、撤回與待領退款

2026-11-19 接續資金／商品對帳；這是 Server 管理政策，不是官方後台規則。

## 行為

管理補發使用目前固定目錄已支援的完整商品選項，另存 ADMIN_GRANT 來源、目錄 SHA、原因及操作 ID，成本為零且不建立假成交。商品進商城保管箱，由原本領取流程進背包；停賣限制新購買，不禁止已支援商品的明示管理補發。特殊功能未支援者不能由補發開放。

撤回只關閉尚未領取的管理補發或舊來源待領權利，原因必填，不變更錢包。舊來源未知原付款，不能冒稱退款。正常付費待領商品走退款：依當時逐商品成交成本，移除該 key 的待領權利並把金額加回原帳號。其餘同批商品不受影響，原成交事實保留。每筆終止只留一個撤回／退款事件。

資產操作、事件與資金紀錄同一 SQLite immediate transaction；請求 ID 保存確切操作內容，避免表單重送重複處置。退款同時寫 Garnet 管理加扣來源及資金鏈，以原 request ID 串聯管理事件與資金。先核對完整待領欄位與來源、無領取／終止事件後處置；不接受瀏覽器提供退款金額。

## 資料與查詢

帳本 definition 升至 LOCAL_CASH_HISTORY_V2，擴充 ADMIN_GRANT 與來源目錄欄。升版在同一 migration 交易中按依賴順序複製並重建商品、領取與格位表，保留所有 key 與歷史，外鍵維持啟用。新增獨立 LOCAL_CASH_ADMIN_ACTIONS_V1，保存 grant/revoke/refund、原因、帳號、商品 key、目錄、金額、前後餘額及 UTC 時間。

`/admin/cash/actions` 使用既有 loopback、防偽表單及 HTML 編碼，可選已支援商品補發、依帳號分頁處置待領項目、查最近管理紀錄。歷史增加補發來源與已撤回／已退款狀態、管理原因；對帳把終止視為已結案權利，而非遺失商品，核對補發／退款與資金來源的一致性。

補發與撤回後遊戲中的保管箱清單需重新登入載入；當次登入的 Garnet 可沿已驗 00A8 重整。後台頁面明示此限制，不捏造即時列表推送封包。舊服務不能完整寫入新管理帳本，Host／Web 須一起換版。

## 界線與待辦

已領取商品需要另行明確歸還／使用狀態與獨立裝備身份驗證；本批不刪改穿戴、倉庫或已消耗商品，也不把此批當成整個商城完成。價格／Client 商品列表配套發布與其他特殊商品仍依接續表。

先驗正常補發→原領取、補發→撤回、付費多商品→逐筆待領退款、舊來源撤回、V1 正常升版及歷史／對帳連貫。重送、拒絕、競爭、故障、安全及壓測保留待測；工程／HTTP 不等於指定 v2 實機通過。

## 本批結果

Host、Web 與檢查器 Release 建置零警告／錯誤；新增兩項 HappyPath 通過，全套 598／598 通過。正常 API 路線包含補發後領取與合併堆疊、補發撤回、兩件同批付款只退一件、其餘正常領取、歷史重開保存及資金對帳；另驗未加值的命名帳號、55 件補發分頁、舊來源撤回不補猜成本。資料外鍵檢查正常。沒有執行重送或拒絕案例。

使用前批已存在的 V1 離線 HTTP fixture，建立獨立副本並由新 Web 正常初始化為 V2；六批成交、55 筆來源、兩筆領取及兩筆格位的原欄位，升版前後逐欄排序雜湊相同，外鍵仍有效。這不是使用者帳號的實機結果。

隔離 Web 用合法 Cookie／CSRF 表單補發一件、撤回該補發、原額退回一件未領 2625／250 Garnet，再撤回一筆未知原款的舊來源；餘額由 6,500 到 6,750，待領由 53 到 51，已退款／撤回歷史與對帳皆一致。另核對待領分頁與目錄補發入口。只執行專用副本，沒有在使用者實際測試帳號執行資產處置。

原測試 DB 的獨立一致副本通過 Host 隔離預檢。確認原 Host／Admin 的 PID、部署路徑及五個 loopback listener 後，保留換版前 DB 副本，一次換成新 Host／Admin。五個商城管理頁皆 HTTP 200，Host 與 Admin 的程式／Persistence 雜湊、帳本 V2、販售、資金及管理處置元件版本均已確認。前批對帳功能同時啟用，Q15 私密隊伍設定保留。

來源、測試、HTTP、升版與部署收據雜湊見 [驗證索引](cash-admin-actions-validation.json)。指定 v2 的補發領取與待領退款實機仍未通過；本批沒有 Client 操作或資源修改。
