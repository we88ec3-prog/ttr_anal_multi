# 已領取商城商品的管理歸還

2026-11-19 接續 CASH-ADMIN-ACTIONS.md。這是管理員明示選擇的 Server 歸還政策，不是官方退款條件或原版 Client 功能。

## 商品身份與使用界線

獨立裝備須找回原領取格位事實中的全部 equipment_id，核對同帳號、同 Product、原身份衍生欄位，且每件只在背包、銀行或某角色穿戴格中出現一次。原件若已失去，不能拿另一件同款替代。歸還保存當時強化狀態，不另退強化材料或費用。

一般堆疊合併後沒有逐件 lot 身份。本管理操作明確接受目前持有的同 Product、相同普通欄位商品作等量歸還，按背包、銀行與格位順序收足原領取數量；不宣稱已證明原批未使用。曾使用的效果不倒扣；必須交回足量現有商品，數量不足就不能完成整筆歸還。本政策不同於直接把已消耗商品原額退款。

只有帳本可識別、已領取、未曾結案、期間／option 與目前支援永久選項相符的商品可預覽。正常購買按原逐商品成交成本退款；補發或舊來源僅回收，不猜未知原付款。未知舊版已領取紀錄不能從目前背包回推成可退款交易。

## 預覽與交易

管理頁先列出已領取歷史，選一筆查看目前來源、可回收數量、背包／銀行／穿戴角色格位、裝備 ID／強化及前後餘額。預覽摘要 SHA 包含來源、目錄、當前錢包與每個回收格位；POST 只提交識別、摘要、原因及 request ID，不接受瀏覽器提供退款金額或格位。

執行要求帳號沒有未到期 Session，並在同一 SQLite immediate transaction 重算來源與回收計畫、比對摘要。帳號新登入與歸還寫入因同一 DB 寫入鎖排序；舊會話不能憑快取繼續通過既有 lease 權威檢查。不強制踢人，不在遊戲在線時改穿戴或背包。預覽後資料有變動須重開預覽，不默默執行不同計畫。

同交易收回確定格位、保存每筆前後數量與身份／強化、清理已無背包商品的快捷綁定、保存歸還事件，並按已知成本寫 Garnet 管理來源與資金鏈。保留原成交與領取事實；本次歸還另外記錄。冷卻、使用效果、其他裝備、其他角色及其他資產不由歸還重設。

## 版本與驗證

獨立 LOCAL_CASH_CLAIMED_RETURNS_V1 保存歸還與格位扣除事實，不重編既有交易 V29 或帳本 V2；歷史增加歸還退款／歸還回收狀態，對帳核對來源、扣除數量與退款資金。

先驗正常購買領取後的背包／銀行堆疊、快捷綁定、原裝備穿戴與銀行歸還、補發回收、前後餘額與持久歷史。登出是本功能的正常前置，不執行重登壓力、重送、競爭、故障、安全或資料破壞測試。指定 v2 的登出→管理歸還→登入後畫面與數值仍需人工驗收；不以 SQL／HTTP 通過冒稱實機通過。

## 本批結果

Host、Web、檢查器 Release 建置零警告／錯誤；三項新增 HappyPath 通過，全套 601／601 通過。堆疊案例從背包 5＋145 與銀行 50 收足 200，保留銀行另 200；清理已空背包商品的快捷綁定並保留另一商品綁定。裝備案例精確收回原穿戴 ID 與原銀行 ID，保留背包同款第三件。補發與已知舊來源領取後只回收，保持 2,000 Garnet、不猜未知成本。各路線正常登出後執行，歷史與對帳保留；沒有執行在線拒絕或摘要過期案例。

另由前批已離線的專用 HTTP fixture 建立副本；不改 Session。合法 Cookie／CSRF 先讀原裝備回收預覽與摘要，再執行 250 原額退款，6,750→7,000，其他已領同款一件保留。原六批成交、56 筆來源、兩筆領取與兩筆格位的原欄位，在新增元件與實際歸還後仍逐欄排序雜湊一致，外鍵正常。這些都是測試 fixture，不是使用者實機結果。

原測試 DB 的獨立一致副本通過 Host 隔離預檢。核對原 Host／Admin 的 PID、部署路徑及五個 loopback listener，保留換版前 DB 副本後一次換版。六個商城頁皆 HTTP 200；Host／Admin/Persistence 雜湊、五個元件版本及 Q15 私密隊伍設定均已確認。沒有在使用者實際測試帳號執行資產歸還，也沒有 Client 操作／修改。

收據雜湊與驗證界線見 [驗證索引](cash-claimed-returns-validation.json)。回到遊戲後的穿戴資源上限、畫面與操作仍待指定 v2 人工驗收；Price／列表配套發布與特殊商品分項仍另列待辦。
