# 條件編排的正常通關旅程

本批接續[訊號與出口介面](SCENARIO-CONDITION-EDITOR.md)，補上先前僅有
編排／保存／匯出、尚未作通關閘門的六種訊號。這是
`OFFLINE_SYNTHETIC_PREPARED_ACCOUNT_APPLICATION_PATH`，內容明示
`NOT_NATIVE_MEF`，不新增原生格式、傳檔 opcode 或 Client 修改。

## 固定來源與七種配置

使用 Case693 原基準 SHA
`594713519e55d88c03573f3ec4e102fcbe0fd6598030a3ab79d414f2d8fa62af`，
既有 AI 原文件 SHA
`fcd7437c891d6ceff3b7584831eb931ab8fe522156cb3cae69def5324cd38701`。
所有圖序、出生點、出口路由、原怪物與掉落來源保持。由固定來源生成獨立
`.scenario.json`，在入口圖3430配置以下正常閘門，每份各走主／分支兩路：

| 配置 | 真正離場前的必要條件 | 結算 EXP |
|---|---|---:|
| RegionEntered | 走進原出口中心、半徑16的區域，設立旗標 | 76 |
| RegionHeld | 在同區域停留2秒，設立旗標 | 76 |
| BagQuantityReached | 正常擊倒並拾取首圖 Product183，已提交背包至少1件 | 76 |
| WaveHealthReached | 初始組血量到75%以下，設立旗標並放出另一隻普通怪物 | 80 |
| ClearDelayElapsed | 完成清場後經過2秒 | 76 |
| CheckpointInteracted | 清場後到同區域，以既有手動機關 category1／鍵11互動 | 76 |
| CombinedSixGates | 六旗標均必要；手動互動另需前五旗標 | 80 |

手動機關另帶可視標記鍵12，出口仍用原鍵10。血量波次由同一初始普通怪物
複製，EXP4，延遲0且必要旗標為血量旗標；沒有新增必要頭目或原生來源。
生怪封包觀察證明增援出現時已有兩隻存活、零隻死亡，故血量條件不是只在
清場後才生效。原必要頭目與分支路線仍照原配置完成。

準備角色、等級、普通裝備與村莊前置使用既有正常路線檢查器；從廣場建隊、
正常進村、選狩獵場、戰鬥、拾取、條件互動、結算及回同一隊伍房間，
經驗與掉落走正常 SQLite 提交。沒有由測試直接寫入場內旗標或注入背包道具。

## 可重現檢查器行為

私有工具 `check-scenario-condition-routes.py` 固定兩份來源 SHA，產生七份
隔離內容與每路 stdout／stderr／摘要；每個輸入與回應各有 SHA。
工具呼叫既有正常路線工具的顯式 `--exercise-scenario-signals` 選項。
此選項限準備帳號正流程與明確指定的配套內容；原預設路線不自動操作機關。

清場、所有怪物實際出現與死亡、掉落提交的驗證維持。新選項在拾取後，
依本圖訊號陣列次序走到區域、對占點等待指定秒數加100ms、對清場延遲等待
指定秒數加100ms、到互動區域發既有 `001C category=1`。這是定向正流程
操作清單，不是任意依賴／屏障／危險區的腳本求解器；錯序或其他玩法不宣稱
可自動通關。出口仍須真正發出開啟狀態，且正常進入事件被接受才算通過。

首次手動互動檢查器誤用 NPC category3，未開出口；核對現有機關處理器後
修為category1，再從頭重跑14路全通過。原失敗收據保留於本機，這是工具
錯誤，不作 Server 機關缺陷或使用者遊戲實測紀錄。

驗證結果見[收據](scenario-condition-gate-routes-validation.json)。本批證明
六種閘門與串接的成功旅程，不涵蓋精確時間／血量邊界、未達條件拒絕、
離區重置、重送、故障、併發及壓測。Client圖示、標記、實際按鍵與新帳號
完整養成仍待指定v2驗收。原生MEF格式／載入鏈缺口仍保留，未因這批閉合。

可重建範例為[六條件串接關卡](case693-six-condition-gates.scenario.json)，
其原始位元組 SHA 與14路收據一起固定。Host／檢查器 Release 建置零警告
與錯誤，632項 HappyPath 通過；未啟用訊號操作選項的兩條Case693基準路線
也各76 EXP。正式遊戲服務、管理端及玩家資料庫都未換版或修改。
