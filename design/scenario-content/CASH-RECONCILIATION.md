# 商城資金與商品對帳

2026-11-19 接續成交／領取帳本與管理接續表。這是 Server 自有資料模型，沒有新增 Client 封包或原生 MEF 主張。

## 資金覆蓋

現有 Garnet 寫入涵蓋管理加扣、商城成交及銀行擴充，不能只用購物歷史推算餘額。獨立 LOCAL_CASH_RECONCILIATION_V1 保存每個帳號自啟用時的餘額起點，以及每次變動的順序、原因類型、來源識別碼、前後餘額、差額與 UTC 時間。啟用前歷史保持未知，不用舊資料重建起始零餘額。

初始化把當前錢包作為起點；之後新帳號的第一次資金變動在同一交易中建立起點。管理加扣關聯原 request ID，購買關聯成交批次 ID，銀行擴充保存獨立支出識別及擴充前後容量。來源事實與資金事件、實際錢包更新共用 SQLite 寫入交易。來源識別碼不以時間戳代替。

每個起點也保存各來源表的 rowid 水位，用來區分啟用前來源與啟用後缺漏；不靠時間戳切界，避免同毫秒事件誤判。新帳號首次建立起點時包含當次已插入的來源水位，該筆仍有同交易的資金事件，不會被當成歷史缺漏。起點不因後續初始化覆寫。

## 唯讀核對

`/admin/cash/reconciliation` 依帳號搜尋、分頁顯示：起始餘額、已記錄差額、預期／實際餘額、資金鏈斷點、來源對應差異，以及商品資料差異。資金事件依遞增序號比對每筆 before 與前一筆 after，不能只比對差額合計，避免相互抵銷的缺漏被忽略。

商品核對逐一檢查待領資料與來源數量／期間／option／time 是否一致、已領與待領重疊、來源無待領也無領取事件、領取格位增加量合計與商品數量不符、成交批次的逐商品金額合計與批次總額不同，以及新資金事件與來源金額／帳號是否一致。舊版來源的未知金額與啟用前缺少資金事件分開標示，不當成新錯帳。若沒有可驗證起點，顯示尚未啟用，不能宣稱核對一致。

本頁不自動修正資料，也不因某筆差異立即變更帳號資產。差異測試、故障、競爭、重送、安全與壓測依目前使用者排程待測；先以正常加值、付款、領取及銀行擴充驗證合計、來源、持久保存與 HTTP 顯示。

## 本批驗證與部署狀態

Host、檢查器與 Web Release 建置皆零警告／錯誤。兩項新增 HappyPath 通過，全套 596／596 通過。正常資金路線驗證 2,000→1,950→1,918→1,843 的管理加扣、兩筆商品同批成交與銀行擴充，並正常領取及重開核對；舊版 schema 啟用 fixture 保留 1,984 起點，另列兩筆啟用前來源，再加值到 2,084，歷史待領仍在。這是正常版本啟用驗證，沒有故障注入。

離線工具新增 `--cash-reconciliation-fixture`，只接受新 DB 路徑。以正常 API 建立 27 個命名帳號／錢包，主帳號有九筆資金事件、預期與實際皆 6,525；商品舊來源 fixture 仍沿前批明確標示。隔離 Web HTTP 核對 25／2 帳號分頁、三種來源、搜尋欄保持與導覽連結。第一次 HTTP helper 使用 PowerShell 保留變數名而中止，finally 已關閉 helper；改名後同組驗證通過。

測試 DB 的獨立一致副本通過 Host 隔離預檢，完成後關閉自建 Host。原在線帳本版 Host／Admin 與其 DB 不變；本批 READY_NOT_DEPLOYED，併後續管理處置一起換版。各差異條件目前只有實作與靜態檢查，不宣稱已跑資料破壞／錯帳注入；實機與負面案例分開待測。收據雜湊、範圍與先前 helper 失敗見 [驗證索引](cash-reconciliation-validation.json)。

## 管理處置接續

後續補發須另存 ADMIN_GRANT 來源與原因，經保管箱正常領取，不能偽裝購買。撤回須針對尚未領取且身份完整的補發／舊版待領項目；付費待領商品退款須按原成交金額、撤銷該筆待領權利並原子加回錢包。已領取商品需要獨立歸還／使用狀態及裝備身份驗證流程，不能逕自扣除可能已交易、消耗或換裝的背包。這些尚待實作，對帳頁存在不代表處置功能完成。
