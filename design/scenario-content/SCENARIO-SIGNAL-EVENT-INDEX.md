# 關卡訊號的事件索引

本批沿用既有 Server schema 與十種 typed producer，將執行時的全表訊號
過濾改成每節點的事件索引。內容與權威仍為 `NOT_NATIVE_MEF`，不是官方
格式復原或 Client 自主戰鬥。這是 Server 關卡執行器的實作調整。

亦不修改任何 Client 資源或宣稱新的 native claim。

## 索引與狀態契約

定義經 catalog 驗證、凍結後，每個 run 建立各節點的不可變查詢索引：

- 事件桶保留原訊號陣列中的相對順序。
- 怪物組觀察桶以本圖 waveId 選取 WaveCleared／WaveHealthReached；
  初始怪物組的 null 識別保持獨立，不與任何有效具名增援混合。
- 手動機關以既有非零鍵查到原 producer，不改 category 或旗標條件。
- 有無占點、背包、頭目、時計 producer 的查詢使用對應索引。

各 run 仍各自擁有旗標、開啟出口、占點起點、圖開始時計及清場觀察時計。
規劃 fork 共用唯讀索引，複製既有 run 狀態；不能因共用索引而寫入原 run。
換圖依新 Node 取得索引，不沿用前圖 producer。事件先後、計時起點、
清場提交後才開始的延遲、含圓周判斷、波血量、袋內數量及出口發布均不變。

未改輪詢頻率或新增 scheduler，不撤除 Server 戰鬥／保存權威，也不減少
既有 wire adapter 命令。本次只縮小每次相關 producer 迴圈的候選集合；
尚未將所有世界邏輯都轉成純事件式執行。

## 驗證及可量測結果

新增混合九訊號的正常流程：入區、占點、圖開始延遲、血量、組清、背包、
清場、清場延遲、手動機關，再由規劃 fork 進下一節點完成。測試核對
正常完成旗標、機關可用、原 run 保留原狀及下一節點 producer 生效。
可選檢查 hook 預設未安裝，不改正常遊戲輸出。

同一流程20次 producer 迴圈選取中，舊全表迴圈對應148個候選槽，
索引回傳19個，減少129個候選槽。這是**相同事件入口的候選集合計數**，
不是實測CPU、總事件判斷次數、Any短路判斷、建置索引成本、封包或DB成本。
不由此推算效能百分比。

既有七種條件配置的14條正常路線重新通過。逐路完整 route 投影與索引前
實際收據相等，包含節點封包清單、出生／死亡／增援、操作清單、拾取、
經驗、出口與下一圖；正常建隊入口及回原房間的投影也相等。這個相等範圍
不是全部wire stream或Client畫面，隨機執行識別與其他未比對欄位不宣稱相等。

結果與檔案SHA見[收據](scenario-signal-event-index-validation.json)。
拒絕、邊界、重送、重入、故障、多人、壓測與Client實機保持既定待測。
原生格式／載入鏈仍未知，但不是繼續 Server 自訂關卡開發的共同阻塞。

Host／檢查器Release建置零警告、零錯誤，633項HappyPath全通過。
三個RAID基準另外正常走完15張圖，分別發2274／2275／2276一本，CP皆維持
3,000，其他資產、裝備、角色經驗與主線狀態保持。這仍是準備角色的
應用層正流程；正式Host、管理端與玩家資料庫本批均未換版或修改。
