# 已存檔背包數量旗標

這是 `SERVER_DESIGN_CHOICE` 的副本條件，沿用 `NOT_NATIVE_MEF` 內容定義，
不是原生 MEF 格式或 Client 自主判定。最新原生入口界線仍以
[MEF 功能追蹤](../../governance/MEF-FUNCTIONAL-COMPLETION.md)的 2026-11-14 整合為準。

```json
{ "flag": "supplies-ready", "event": "BagQuantityReached", "product": 201,
  "quantity": 3 }
```

`product` 是既有 Server 背包的非零 uint 道具鍵，`quantity` 是 1 至 255 的整數。
本例鍵只是契約示例，正式關卡須對照道具來源。此事件不接受區域、互動、時間、
波次或血量欄位。讀取目前授權 Session 的已提交背包快照，跨堆疊加總同鍵道具；
銀行、商城待領倉、裝備欄及未拾取地面掉落不計入。不消耗、不授獎、不代交任務。

節點進入且開放戰鬥／出口操作後觀察，劇情鎖定或主線提交未完成時不觀察。
首次達到門檻即設立實例旗標，之後用掉道具不撤銷。它表示「曾達標」，
不能當成持續持有檢查或扣道具交易。旗標隨既有實例分支與主線提交副本保存；
副本重開依原規則重新建立，不新增斷線續關政策。

正常連線的世界更新透過既有授權資產存取介面讀值，尚有未達成條件時每 500ms
至多讀取一次；下一次世界更新公布已滿足的互動、屏障、增援或清場出口。
沒有待觀察條件時不讀背包。授權讀取未返回快照時不設立旗標。
出口開啟仍走既有清場、座標與旗標發布流程，不能提前消耗開門更新。

靜態圖檢查只證明條件依賴可達，無法證明玩家一定持有道具。作者須提供可取得的
道具來源，或清楚列出入場攜帶需求；不得讓唯一掉落來源又被此條件封鎖。
正式關卡部署、道具取得與 Client 點位更新須另列實機驗收，不以合成測試代替。

[單一訊號 Schema](bag-quantity-signal.schema.json)只驗證此訊號的資料形狀，
完整場景仍須通過 Server 的圖、幾何與來源驗證；舊版條件 Schema 不宣稱支援此擴充。
