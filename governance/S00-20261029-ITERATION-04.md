## 4. 雙重審查通道：不可混用

**T01 來源／原生主張通道**：使用原始版本、精確 Git blob、VA/raw/CFG/caller/callee、反證及已知 T01 裁決，必要時 R2/R3 定向驗收；`FULL_PASS_DOCUMENT_SCOPED` 仍採原本嚴格門檻。`FAILED` 不能直接翻成 FULL-PASS，新的 bounded claim 也不替代原始全文結論。

**S00 契約通道**：只決定某 RR 有沒有交到其限定問題的可追溯證據，是否轉入 SPEC 的某段 Client-compatible 要求；即使 S00 `ACCEPTED`，GAP 是否 `RESOLVED`、SPEC 是否 `REVIEWED/STABLE`、TEST 是否由合成升級、ADR 是否批准，全都要單獨審查，不可聯動。

當研究回報其實只證明「缺口仍無法閉合」，不能假裝新增 opcode；可以留 `NEEDS_REVISION`、`BLOCKED`（寫明解除條件）或按窄義研究交付做明確決議，同時 **GAP/COV 保持 BLOCKED**。

## 5. S00 正式 RR 審查 Checklist

### 5.1 最低可接受來源身份

- 一致的 KR/TC、原始 Client SHA256、來源路徑、**來源報告在 Git 的 blob SHA**，報告實際存在並可重新取得。
- 對每個技術主張指出精確實作位置、前提、正向/反向路徑、證據限制與可信度，不能單憑「搜尋過」即通過。
- 實際網路外框與本地 buffer、命令與資料欄位、Client-local resource 均分離標記；已有 T01 退回或 E14/E15 修正時明確採最新版。

### 5.2 最低可接受 Server-facing 合約資訊

- 若是 C2S/S2C：方向、frame marker、command、packet stage、連線/slot/mode、payload length/offset/encoding、必要 guard、Client 消費者/發送者。
- request/reply 成功與失敗分支都有可追溯證據；不夠就確切指出 `UNKNOWN` 的欄位與解除條件。
- 受影響 SPEC、CLM、GAP、COV、TEST 的 ID 與版本皆存在；證據不允許跨 KR/TC 同位址沿用。
- 不把自訂 Server 帳號/資料庫/Session 策略推定為原官方行為；可作 ADR 提案但需保持 non-normative。

### 5.3 審核／上架隔離

- 研究者提交實際檔案與提交後的 blob，再請 S00/T01 進入 `IN_REVIEW`。
- T01 有界原生查核 ≠ S00 RR 驗收；兩者分別留紀錄。
- S00 的 review card 記錄逐項已證/部分/未知/反證及明確決議；進入 `ACCEPTED` 前符合該 RR 的 acceptance criteria。
- 先記錄方向別 SPEC 與獨立可理解的 TEST，再審查 GAP 關閉；仍有 blocker 不發布 STABLE。
