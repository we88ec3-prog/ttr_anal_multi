## 2026-11-14 傳送時機複核

**目前沒有任何已確認能由遊戲 Server 把原生 `.mef` 傳給 Client 的時機。**
已定位的時點可交付載入畫面索引、入場交握、Case／地圖 ID 和任務／場景鍵，讓 Client 使用既有資源。

### 副本面板的另一條出站路徑

`CMapViewMissionPanel` 的第二個按鈕分支發本機事件 `F42F0`。沿保存的 Ghidra 結果，`5B0760` 在收到該事件時把面板 `+308` 交給 `596E00`，後者依本機面板狀態走 `596EC0`。原始 KR BIN 和指定 v2 在 `5B0781`、`596E7F`、`596E95`、`596EB1` 的直接呼叫目標相同。兩版 `596FA6` 起也都以 `C7 45 08 49 00 01 00` 寫入固定四位元組，在 `FBA798` 狀態允許時，經 `FBA854` 的 vtable `+10` 送出 **C2S `49 00 01 00`**。

### 已知檔案下載與另名封裝檢查

韓版遊戲程式有實際寫檔的 HTTP 路徑。登入公告 `4E59D0` 將 `Notice.xml` 下載至 `Notice.xml.tmp`。徽章工作迴圈 `4E7D40 → 4E7DB0` 處理有下載旗標的項目並寫入 `Emblem/*_S.bmp`。排行榜 `4FA9F0` 下載 `CR_*.txt` 和 `BR_*.txt`，寫入 `Rank/` 下無副檔名的快取。原版啟動器另有啟動前的更新清單流程。這些路徑目前只確認各自的用途，遊戲內副本轉場的封裝下載仍未定位。

為查「STP 封裝是否改了副檔名」，以檔頭識別，讀取韓版 `origin` 的 5,614 個及繁中 `tc_workspace` 的 2,239 個非 `.stp` 檔案各前 4 bytes。略過路徑中有點開頭的項目，無讀取錯誤，兩邊均無 `STPD` 檔頭。這個檢查涵蓋原樣改名且從 offset 0 開始的 STPD，尚未涵蓋檔案內嵌、額外包裝或其他容器格式。

補查指定 v2 使用的本機 `fcs.flu`、`pack.gms`，兩檔與韓版原件 SHA-256 一致。再比對繁中版本，`pack.gms` 相同，`fcs.flu` 不同。以 ASCII／UTF-16LE 查這些檔案全長，均未見 `STPD`、`STPI`、`.mef` 或三個已知關卡鍵 `N_mushroom01_01N`、`N_mushroom12_01B`、`S_pathofpindus01`。兩版 `Integrity.xml` 均把 `Field.stp`、`Event.stp`、`fcs.flu`、`pack.gms` 列為獨立更新項目，各列含檔名、長度與校驗值。這支持啟動前可按封裝整份更新。此輪僅比對清單與可見位元組，未解碼 FLU／GMS 格式，也未證明指定 v2 直接啟動會走原版啟動器的更新流程。

原始韓版 `Field.stp` 的 1,540 個成員全為 XML，內有地圖路線和怪物群組。 `Event.stp` 含 1,840 個 `.seq`、3 個 Lua 與 5,535 個相機檔。 `BoundMap.stp` 有 1,296 個 `.bnd`。這些證據確認多份關卡相關資料確實以封裝分發，仍未找到原生 `.mef` 內容。後續查不同格式的容器時，應從讀取器及可識別的關卡鍵往回追來源，例如 `N_mushroom12_01B`，而非只靠副檔名。

### 同地形切換時的 ID 與資源消費

再核對換圖函式 `4DF510..4DFA9B`、碰撞載入和兩個音訊入口。四個檢查視窗在原始 KR BIN 與指定 v2 中逐位元組一致。原始反組譯與 Ghidra 偽碼支持以下區分。

以上辨認出同地形切換時仍保留的邏輯地圖 ID，以及模型、碰撞、音訊各自的消費者。這些入口未從不同的 TRIGGER 值選出可執行資料。接續查核應比對不同場景控制器如何消費同一個邏輯 ID，並保留各副本的 ID 作為 Server 配置索引。

### 一般副本啟用事件的下游

沿用已保存的 Ghidra 偽碼，以原始 KR BIN 及指定 v2 複核四個指令視窗，兩版皆一致。一般副本的 `0014` 在 `42311F` 先進共用的 `4B2570`，在 `42315E` 再經 `58AAD0` 發本機事件 `F4262`。主線副本的啟用槽直接走共用入口。

- 共用入口將目前控制器 `+4` 設為 1。`4B25B5` 可初始化場景管理器並讀本機 `CSL.scn` 的已看場景鍵。`4B25E8 → 6D0750 → 6D08F0` 的 XML 分支是 `KeyMapping` 初始化。這兩條路徑未從 `0014` 或地圖 ID 取新的資源名稱。
- 已找到的 `F4262` UI 消費者 `5AC600` 在 `5AC6B7` 把固定事件鍵 `F4321` 交給 `58B350`。在 `58B3AF → 753440` 走 UI 元件清單，以該鍵匹配元件事件。此路徑未接收 Server 檔名或資料緩衝區。

因此這兩條場景啟用分支目前沒有可用的 `.mef` 傳入欄位。Server 可用 `0014` 讓控制器就緒，怪物建立則有獨立的 `0007` 消費者。這輪未確認原服兩種訊息的先後，也沒有執行指定 Client；不從場景啟用時機推定原服生怪時序。

### 一般副本結算的固定資料區

追查 `CMissionDescData` 的全域指標 `FE1AA4`，在原始 KR BIN 的 `.text` 找到五處絕對位址引用。三處是建構／清理，另外兩處落在結算接收器 `4BC2D0` 與 UI 的 `653D90`。兩處使用視窗與指定 v2 逐位元組相同。

- `S2C 0022/type 2` 的 `4BC329..4BC351` 從封包 `+4` 複製固定 26 bytes 到結果場景，再複製到 `CMissionDescData+8`。此已核對分支要求應用資料至少 30 bytes。它不是副本進場時寫入的選關資料，也沒有在此拷貝任意長度的內容。
- `653DFE / 653E3B / 653E78 / 653EB5` 取 `CMissionDescData` 的 `+0C / +10 / +14 / +1E`，各交給 `40EF80` 轉十進位文字。對應封包 DWORD 偏移為 `+8 / +12 / +16 / +26`。仍需對照各欄 UI 標籤，才能指定獎勵的含義。封包 `+24` 的結果分支值為 1 或 2 時會進結果背景；值 0 走 `C2S 0019` 分支。不可只把主線結果的 type 從 0 改為 2。

現行 Stage 1 本機測試仍借用主線的 `0022/type 0` 候選。正式練等時，Server 持久化的經驗值與 Client 的 type 2 顯示欄位須分別驗證。另有 `0038 → 4B1BF0` 可確認先清空舊場景上下文，再從 Server 封包填入 Stage／Case；現有 `F439E` 出站分支只帶固定值，尚未辨識玩家選關值如何到達 Server。以上未建立 `.mef` 可傳入的時點。

#### 可重複副本的 Server 經驗入帳

副本實例由 Server 配發唯一識別碼。通關時由當前有效連線與參戰角色提交經驗，使用帳號與實例識別碼作唯一鍵。經驗記錄與角色總經驗在同一資料庫交易內更新。每次新通關可增加經驗，同一實例重複提交不增加經驗。主線仍按原有帳號與任務鍵記錄，兩者共用同一角色經驗曲線及累計值。

這是 Server 持久化決定。現有 SQLite 需重跑可重複執行的角色經驗元件遷移以新增副本紀錄表，既有主線表和角色資料由原格式保留。正常入口接通後，應以已提交的獎勵組一般副本結果，並更新角色經驗快照。進度指定仍不入帳，正式獎勵數值與實機畫面另驗。
