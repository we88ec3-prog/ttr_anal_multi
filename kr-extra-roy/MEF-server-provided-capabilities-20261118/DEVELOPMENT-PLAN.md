# MEF 開發優先序：先交付能力，再擴充下放範圍

本輪重新定義 P0／P1／P2，以使用者要求的 Server 提供內容、MEF 優先處理為準。它們是**開發／整合順序**，不是官方格式復原順序；舊版同名優先序保留於歷史包，不能混用完成狀態。

本包完成的是能力與接口的重新分析。現有 Server 能力直接復用；新 Client MEF 發布、接線與人測仍分列。所謂「完成一階段」必須是下表具體結果成立，不能用文件或合成案例數替代。

## P0：把一段新的 MEF 內容真正接入現有流程

| 工作 | 分析結論與實作方向 | 完成判準 | 尚需的具體輸入／整合 |
|---|---|---|---|
| P0.1 內容版本與交付 | 先用已證的啟動前發布／資源 resolver，再由既有 scene 雙鍵選擇 finite Q；不用等官方 `.mef` 或新 raw-script opcode | 新內容與完整有效索引有同一版本；Client 選中的是所發布 bytes；實際 selector 無衝突 | 選一份合併索引、綁定新鍵／名稱及實際發布路徑；不能假定 loose file 會覆蓋 STP |
| P0.2 有限內容作者契約 | prepass 只處理依賴；正式 coroutine 執行本地等待、既有點操作與明確 End。可加已證的演出能力，不必等 ordinary B | 一次啟動後內容自行完成預定步驟與收尾；Server 沒有逐步派同一組效果 | 所選 point 必須已在場景中；literal 於建置時綁定；Start／End／解除等待按已有接口接好 |
| P0.3 復用現有規則引擎與保存 | Entry／GroupCleared／InteractZ、Scenario／MonsterBehavior、結算／資產／任務保存已是 MEF／Server 基礎。新規則接這些 adapter | 一個新內容版本能從條件到動作再到既有完成／保存入口；不新增另一套逐關硬編碼 | 編譯／映射規則、完成依據與當前 run／內容版本對齊；Q 完成只表示該事件結束 |

**P0 的玩家結果：**進入一段新內容後，提示／等待／開門等步驟由內容自己接續；退出後任務與獎勵沿既有系統保存。最小試點可不生怪、不載新模型，以免把不相干的資源欠缺變成共同阻塞。若由已存在的 Server MEF 接到群清，可在適用時點一次 `0047` 選新 finite 內容，Client 自行完成後續演出及開門，無需通用事件注入 Lua；純單項開門也可沿一次 `0048`。兩者都由 MEF 規則決定，不讓 Server 接管整段時間線。

P0 不需要先解出 Q119 的全部歷史模型、官方 Field MEF 或普通場景背景 Lua；它只需要所選發布品真正使用的依賴。範例和輸入契約見 [內容作者契約](delivery-profiles/authoring-contract.md)。

## P1：把關卡玩法拆成可下放的規則與執行

| 工作 | 分析結論與實作方向 | 完成判準 | 尚需的具體接口／內容 |
|---|---|---|---|
| P1.1 生成與行動 | `lb.CreateObjectEx` 的普通模型分支生成 world `CMonster`，而 native frame 鏈可自行更新動作；把排程／高階指令放 MEF | 所選本地用途可由 MEF 生成與驅動；需要共用物件時身分與生命期能對齊 | 模型及位置依賴；需要敵對 AI／共享 ID 的用途依 world 報告補接口，不能把 attach 參數當敵方腦開關 |
| P1.2 戰鬥與敵群清空 | MEF 定義技能／波次／清場規則；優先復用目前 Server 規則與 world adapter、Client native 動作。只有事件／查詢可達時，才把該決策移至 Client MEF | 對同一套內容能觀察真正 HP／死亡／指定群清；該條件驅動後續內容；逐步控制量可比較 | 普通世界死亡／群組事件至 Lua 的通路、必要 EntityId／代次、合法技能／命中輸入。不能用 count stub、Q 停止或傷害面板代替 |
| P1.3 出口、NPC、任務與獎勵完整串接 | 既有點可由 MEF setter 開放；Server MEF 收群清後可用既有 selector 啟動 finite 清場內容；NPC／服務／任務條件由內容配置；結算規則接已有資產與進度 adapter | 生怪→戰鬥→群清→開出口→結算→獎勵與保存走通選定正常流程；每段使用同一內容版本 | 實際關卡幾何、服務表與依賴；新 finite 內容與點／版本綁定；結果頁、返回和獎勵／前置發布順序；新 MEF 與現有保存的差額 |

**P1 的玩家結果：**怪物、波次與出口由關卡內容安排；清怪後會觸發下一段，完成時發放並保存正確結果。這不要求所有決策立刻都在 Client：尚缺 Client 事件橋的部分可先由 Server MEF 規則執行，仍屬 MEF 開發；接到可證接口後再移動執行位置。

普通 Mission／Scenario 的常駐 Lua B，只在確實需要「保留普通操控、長期執行任意背景腳本」的功能時處理。不要拿它擋已可使用的 finite Q、Tutorial 或 native 持續效果。接續靜態問題必須限定到具體 caller／writer／consumer；本輪 world 報告保存已查範圍與排除候選。

## P2：把可用內容變成可重用的開發管線

| 工作 | 分析結論與實作方向 | 完成判準 | 尚需的工作 |
|---|---|---|---|
| P2.1 一份規則、多個執行落點 | 在既有 schema／catalog 上加內容建置：Client 相容 sequence 與 Server 規則共用版本／邏輯鍵。不是讓原 Client 直接讀新 JSON | 同一內容定義可產出被選中的 Client 內容與可載入的 Server 規則；沒有兩份互相漂移的關卡常數 | 沿用現有外部配置與 SHA 機制，擴充必要 schema／compiler／檢查器；編輯器可後續接，無需先另做管理站 |
| P2.2 多人和反覆使用 | 以所選 profile 的真實生命期配置 run、內容版本、共同事件與本地效果 | 共同條件與各端畫面一致；反覆遊玩不因 seen／owner／舊版本而誤跳步 | 先使用現行同步和任務實例；特定 profile 的重入問題按已證機制解決，不假造通用 ACK |
| P2.3 進度與內容演進 | 既有里程碑／資產保存優先復用；新規則需版本相容與明確恢復點 | 更新內容後已保存進度仍能依已定政策繼續；正常完成不重複入帳 | 版本轉換與新節點里程碑；未完成副本是否中途續玩是明確功能選擇，不把保存整個 Lua VM 當預設 |
| P2.4 用數據確認減負 | 比較等價正常流程的 Server 排程、命令、bytes、CPU 與 DB 提交；同時看 Client 成本 | 能指出哪項工作真的減少、哪項只是資料化，不捏造百分比 | 接既有記錄後收集正常流程量測；壓測／併發／異常測試仍照專案日後排程 |

**P2 的玩家結果：**更多關卡可由同一套內容工具製作，版本更新後進度可持續使用，並能確認改動對遊戲流暢度與 Server 工作量的影響。

## 歷史 P0／P1／P2 如何接續

| 歷史研究 | 本輪處置 |
|---|---|
| 資源選取、Master mount、FCS／base 資源鏈 | 當作發布與依賴解析的已知基礎；缺失只約束實際使用該依賴的內容 |
| UI factory／owner／清理與生命期 | 沿用已證契約；需要該視窗時再滿足實際資源，不泛化為全部 MEF 阻塞 |
| 原生 parser／Lua 入口／pump／prepass | 直接用於自製內容設計，不為了官方名稱重掃全部 sink |
| 官方 MEF grammar／Field 檔案 | **退出目前目標**；不宣稱已復原，也不列新 MEF 必要材料 |

完整分析結果與缺口按「Client 待逆向／MEF 與 Server 待開發／跨功能待整合／待遊玩驗證」分列。上 Git 代表這份分析與契約已交付；不改寫其他工作線的實作或驗收進度。
