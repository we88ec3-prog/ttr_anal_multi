# 給玩家看的 MEF 進度與缺項

MEF 可以理解為 Server 提供的關卡內容：決定什麼時候出怪、過了哪個條件接哪一段、什麼時候開門、完成後拿什麼獎勵。**這些都屬於 MEF／Server 開發。** Client 能自己完成的部分優先交給它；需要共同狀態或保存的部分，讓 MEF 規則接上現有 Server 服務。

本輪已完成這個方向的重新分析並整理成可實作契約。舊的「要先找到官方 MEF 才能往下做」已移出目標。這份進度不把分析、既有實作、新內容接線與實際遊玩混成一個百分比。[完整報告](REPORT.md)

## 七項主要功能

| 玩家在遊戲裡看到的事 | 現在已確認／已有的部分 | 還缺的部分 |
|---|---|---|
| **怪物出現** | MEF 可安排本地生成；生成的是進入世界更新的怪物物件。Server 也已有內容化出生與波次 | 新內容真正接入；模型／位置資料；如果要讓這隻怪共同參戰，還要對齊物件身分、控制與事件 |
| **怪物移動、攻擊與扣血** | Client 已會自己推進移動和動作；Server 有可復用的行為與戰鬥規則 | 把敵方決策或命中再移給 Client MEF，需要實際可讀寫的接口。看到攻擊動畫，還不等於已算完命中和扣血 |
| **打完一群怪，接下一波** | 現有事件引擎已有清組、波次與旗標；這些規則可以由 MEF 控制 | 普通怪物死亡／指定群清的事實如何直接交給 Client 腳本尚未閉合。現階段可先由 Server MEF 收事件後推進 |
| **清怪後門打開** | MEF 已有能切換既有出口的動作。Server MEF 確認清怪後，可只通知一段內容開始，Client 自己完成等待、演出與開門 | 出口、這段內容及啟動鍵要先配好；此方案不用等待通用背景事件接口。若只要開一扇門，也能沿現有的一次更新 |
| **任務完成並結算** | 主線完成事件、普通任務的接取／進度／完成服務已有 | 把新 MEF 的完成條件接進既有服務；不能只因劇情播完就當成真的通關 |
| **取得經驗、錢和其他獎勵** | 已有經驗、錢包、熟練度與資產保存／發布接線，獎勵規則可放 MEF | 新規則、內容版本及實際受益角色接線。顯示獎勵和獎勵已入帳要分清楚 |
| **關遊戲後進度還在** | 已有任務、主線、成長、資產與獎勵帳本保存 | 將新 MEF 的里程碑接入同一份存檔；若要求戰鬥打到一半也能續玩，需另外定義保存點 |

來源：[生怪／戰鬥分析](world-offload/report.md)、[出口／任務／獎勵／保存分析](npc-progression/report.md)、[既有成果復用](SERVER-REUSE.md)。本輪沒有重新宣告那些既有 Server 功能全部缺少，也沒有宣告新 MEF 已經可玩。

## 不只打怪：還能交給 MEF 的內容

一次啟動一份有限內容後，Client 可自行安排等待、角色動作、鏡頭、聲音、圖片、對話與畫面效果，再操作已存在的點位及收尾。真正的 Tutorial 流程也能依玩家走到位置或完成指定互動繼續下一段。這些能力已有原件依據，不用等普通場景背景腳本全部研究完。[執行路線與作者範本](delivery-profiles/authoring-contract.md)

例如「打完這波 → 播清場內容 → 等待 → 開門」，可以讓現有 Server MEF 負責已經接好的清組條件，只啟動一次內容，後面的細節都交給 Client。這與要求 Client 自己判定所有怪物死亡是不同的開發範圍；前者已有可用接口可組合。[完整流程](REPORT.md)

本輪完整對照了 121 個正常接口及 15 個功能域；其中有 4 個名稱實際是空操作，另有 1 個名稱不能取得物件數。文件會把這些限制指出，避免開發時用名字猜功能。[全功能表](BINDING-OFFLOAD-MAP.md)

## P0／P1／P2 現在代表什麼

| 優先序 | 分析進度 | 玩家目標 | 下一段缺項 |
|---|---|---|---|
| **P0** | 交付、入口、有限內容與既有保存接線的規格已整理 | 一份新內容可自己接續提示／等待／開門，接回原有任務流程 | 真正內容版本、啟動鍵、點位、發布選取與正常流程整合 |
| **P1** | 生怪、戰鬥、清組、出口、結算的能力與接口已拆清；普通世界事件進 Client Lua 仍有明確缺邊 | 做成能從入場一路玩到領獎的完整關卡 | 新規則與現有 world／事件／獎勵服務接線；需要 Client 自主決策的接口；實際關卡素材及驗收 |
| **P2** | 共用製作、版本、保存與減負的規劃已完成 | 更多關卡用同一套內容工具製作，更新後進度能延續，也能確認 Server 工作量是否降低 | 建置管線、版本相容、選定 profile 的反覆使用／共同狀態、正常流程量測 |

完整工作與完成判準在 [開發計畫](DEVELOPMENT-PLAN.md)。官方檔案復原沒有排在這三階段之前；仍待完成的是具體內容、接口和實際整合。

## Server 會少做什麼

最直接的收益，是不用為同一段演出的每個步驟持續計時或逐步下指令。關卡規則放入共用 MEF，也能減少每關各寫一套程式。若判斷仍在 Server 上跑，運算量不會因換了規則檔就消失；真正省多少，需比較相同玩家流程後才能報數字。[量測方式](LOAD-REDUCTION.md)
