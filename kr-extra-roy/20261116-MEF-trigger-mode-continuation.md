# MEF R13 — 互動點自動／按鍵觸發、重用狀態與場景再入

研究日期：2026-11-16（Asia/Taipei）。工作分支：\`extra/roy1\`。承接已公開 R12 \`35ae91f69715ff67a101dba2d1cf14b0fed460ae\`。本輪用途是保存前次中斷前已定位但未提交的**可核原件增量**，不是重發 R12，也不把資料推進稱為已完整還原官方 \`.mef\` 格式。

## 1. 進度與證據邊界

本輪重新從實體 KR \`Tartaros.bin\` 驗證 PE32/i386 原件（SHA-256 \`9741d1975327b9309d82b52f631165bc410757694d7c183a5eed970a53ebef91\`），依 \`.text\` VA \`0x401000\` ↔ raw \`0x400\` 做 address mapping；擷取原生 machine-code windows，另保存[12 組節錄與 raw 地址](MEF-trigger-continuation-20261116/evidence.json)。既有 R12 [完整點集合、S2C 0027/0048、Lua setter 與部分 C2S 001C](20261116-MEF-checkpoint-lifecycle.md) 作為已證基礎，不重列全部。

本輪直接閉合的是**互動點被選入候選的狀態機**，以及候選如何交回類別分派端。除已證 native writer/reader 之外，本輪沒有找到 \`point+0x104\` 的 Lua 公開 getter；因而它**只能被稱為 Client 內部進／出範圍狀態**。先前中斷時曾提及「腳本可查旗標」，目前不能單憑該短句或 native 標記，斷言是這個位元組。若要確認腳本 getter，須有明確 registrar→closure→getter 的正向鏈，或可合法解析的原版 Lua consumer。

## 2. 逐條原生分支與資料流

### 2.1 同一點的主要欄位

原生 point constructor \`0x543700\` 寫入 \`+0xF4\` category、\`+0xF6\` key、\`+0xFC\` 半徑、\`+0x100\` 觸發模式、\`+0x105\` 啟用狀態，並於 \`0x543787\` 把 \`point+0x104\` 初始化為 **0**。對於一般 category，既有來源提供 XY。此處 \`+0x100\` 是 DWORD；\`0027\` row 的第一個尾位元組會作為輸入，不能擴稱任何整數都是官方定義的模式。

### 2.2 \`0x544730\`：是否可成為有效觸發候選

這個 helper 是 \`0x544A00\` 候選搜尋會呼叫的 native；它不直接執行 NPC 對話或商店交易。

- \`0x544739\`：若 \`point+0x105==0\`，回 0，並將一個輸出參數寫 0。**此分支不清 \`point+0x104\`**；所以「停用」不能等同完整重置進出範圍紀錄。
- \`0x544750–0x544792\`：根據玩家／point 兩個 XY 算平方距離，與 \`(point+0xFC)^2\` 比較，得到是否在範圍內（相等的邊界依 \`fcomip/jbe\` 條件，不應誇成精確地理單位）。
- \`0x54479A\`：檢查 \`point+0x100\` 是零或非零，分開判斷觸發模式。
- **mode==0：** \`0x5447A3\` 要求傳入的輸入條件（\`[EBP+0x10]\`）非零，而且本次在範圍內；不滿足時到 \`0x5447E0\`，將 \`+0x104=0\` 並返回 0。滿足時若 \`+0x104\` 已非零，會把候選輸出旗標寫 0；接著寫 \`+0x104=1\` 並返回 1。
- **mode!=0：** \`0x5447CE\` 在範圍內會走同一條置 \`+0x104=1\` 的成功路徑，**不經前述輸入條件檢查**；範圍外則在 \`0x5447D2\` 比較 \`+0x104\`，依分支處理輸出，最後到 \`0x5447E0\` 將 \`+0x104=0\`。
- \`0x5447BC\` 的先前已在範圍標記配合輸出參數，可讓每次更新時返回 1 但不持續造成同一個「新候選」事件；因此要**區分 helper 的返回值與可送往分派的輸出位元**。

**名稱限制：**這是「mode 0 有輸入條件、非零模式不要求同一輸入條件」的已核原生行為。暫可在內容／Server 設計上稱「輸入觸發／入範圍觸發候選」，但**不推定 mode 0 必然是鍵盤 Z、也不把任何 mode 非零值都定義為相同官方 enum**。還需要上游真正輸入 producer 與資源 row 的具體值才能完成玩家操作對映。

### 2.3 \`0x544A00\`：選取最近有效候選，再分派到各 category

\`0x544AA1\` 呼 \`0x544730\`，隨後：
1. \`0x544AA6\` 先檢查上一節的**輸出旗標**；
2. \`0x544AAD\` 也檢查 helper 回傳；
3. \`0x544AB1..0x544AD1\` 比較候選距離並保存最符合條件的 point；
4. \`0x544AE3\` 取選中指標；\`0x544B1D\` 檢查全域頁面／輸入 gate，符合時呼叫 point vtable \`+0x64\`；
5. 既有 R12 已將該 vtable 指向 \`0x544070\`，依 category 處理 NPC／商店／教程，只有部分 fallback 會送 \`001C\`。

這表示 **點已經啟用＋人在範圍內仍不等於每個 frame 都會開始互動**；還要符合輸入／上次範圍旗標／候選勝出／current context 的條件。多點重疊時，不能從 key 順序推論一定是哪一個被觸發。

### 2.4 舊狀態如何重用／清除

\`0x543787\` 的 constructor 確定把 \`+0x104=0\`；\`0x5447E0\` 在已啟用且合法執行該檢查的落空／離開分支也把它清零。相反地，\`0x544739\` 的**停用早退**並不清零。由於 S2C \`0027\` 的 \`0x5449A0\` 會釋放舊 point 並重新建立集合，重建新點的 constructor 才能確定得到初始 0。S2C \`0048\`／Lua \`SetCheckPointStatus\` 只更新既有點狀態，**不會因更新而新建一個狀態乾淨的 point**。

因此原本已在範圍內而被停用的點，重新啟用後的首個觸發是否會立刻重新成立，取決於當次輸入、距離與殘留 \`+0x104\`；不能宣稱任意停用／啟用就保證新的 one-shot event。具體可重現案例要依本段二種 mode 的分支逐一測試。

## 3. 可直接交給內容與 Server 開發的功能契約

| 情境 | MEF／Client 已確認可做 | Server 待開發／必要條件 |
|---|---|---|
| 角色走入指定提示範圍，啟動教學或劇情 | 已建點的非零 mode 可不等同輸入鍵而依距離選入候選；仍受頁面 gate 約束 | 完整 \`0027\`、合法 (category,key,XY,radius,mode)、場景上下文與教學結果 |
| 玩家需要操作才能互動 | mode 0 在有效距離內還要求輸入條件 | 原生輸入 producer／操作 UI 的整合；不猜按鍵名稱 |
| 劇情後開放／鎖閉商店 | Lua \`SetCheckPointStatus\` 或 Server \`0048\` 修改既有點 | 運作前先 \`0027\`；狀態值與持久化、重啟場景同步 |
| 多個 NPC／Shop 點重疊 | \`544A00\` 以距離及候選旗標選出單一點，再執行 category handler | 正確點位與半徑，避免不預期競爭；一次只依原路由處理 |
| 重新進場、重新開放提示 | 新建點重設 \`+0x104\`；局部 setter 不建立新點也不保證重置 \`+0x104\` | Server 依最新權威資料發布完整 snapshot，適當保護 0048 時序 |

### Server 需求（非原版 Server 內部演算法主張）

- **S-TRIGGER-1：**完整保存／重發 S2C 0027 的全類別點清單，不能只更新一項服務而抹去其他互動點。
- **S-TRIGGER-2：**依合法 (category,key) 管理 S2C 0048／Lua 啟停先後、state 0/1 與場景 generation；完成結果不得從 \`+0x104\` 本地邊緣狀態推定。
- **S-TRIGGER-3：**商店、教學、出口、任務進度及交易結果仍依相容 Server 的原生請求／回覆、業務規則與持久化，不把本地提示亮起當任務完成。
- **S-TRIGGER-4：**針對 mode 0、非零 mode、進出範圍、停用中返回／再啟用、重建集合，以及多點重疊訂正常流程 trace 與驗收。

## 4. 尚未閉合的證據與不能聲稱的能力

- **Client 待逆向：**輸入條件的上游具體鍵位與 context；原版 Lua 是否有 getter 能讀 \`point+0x104\` 或其他獨立教程結果；官方 \`MapList.TRIGGER\` 到 \`.mef\` loader／格式／executor。沒有這些正向鏈，不能宣稱前次中斷提到的「腳本可讀旗標」已與本欄位完全相連。
- **Server 待開發：**上節四個具體需求、資料來源與回覆；原版 Server 的內部決策未知本身不妨礙 Client 能力使用。
- **跨功能待整合：**合法的新內容 caller、SceneList 入口、prepass/formal、互動點 category handler、原商店與任務服務。
- **待遊玩驗證：**執行兩種 mode、局部 disable/re-enable、完整 0027 重建、多點競爭及 UI/packet 結果；目前只做唯讀原件分析。

本輪沒有啟動、修改或附加原版 Client，沒有執行 Lua/Server，沒有自行編造官方 .mef 格式或新網路 opcode。有限原件節錄的 PASS 不是 T01 FULL-PASS／RR ACCEPTED／Server 已實作或遊玩驗收。
